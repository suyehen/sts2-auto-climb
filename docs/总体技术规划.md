# AutoSlayTheSpire 总体技术规划

日期：2026-10-08
状态：游戏桥接已实现；决策计算层第一阶段已开始实现
修订：补充知识检索、构筑评估与计算辅助
目标平台：Windows、Slay the Spire 2、Codex 本地会话

## 1. 项目目标

构建一套连接《杀戮尖塔 2》与 Codex 的工具，使用户在 Codex 中发出“开始游玩”后，Codex 能读取游戏状态、决定每一个有意义的游戏选择、执行操作并检查结果，逐步完成一局游戏。

“每一步由 Codex 决策”包括出牌、攻击目标、药水使用、结束回合、卡牌奖励、路线、商店、休息点和事件选择。鼠标移动、等待结算、参数校验和通信恢复属于程序的机械执行工作。

本项目不训练模型，不建立独立策略机器人，不让本地程序在失败时自行选择替代动作。正常游玩的决策来自当前 Codex 会话。

首版使用单人模式、固定角色和基础难度。多人协作、完整机制模拟器、自动训练、极限胜率优化和无人值守无限运行不进入首版范围。

## 2. 成品使用流程

1. 用户安装桥接模组，配置本地 MCP 服务。
2. 用户启动游戏和 Codex，进入可游玩的游戏状态。
3. 用户授权 Codex 开始游玩，并可指定角色、目标或策略偏好。
4. Codex 获取状态，按需查询机制资料和计算指标，选择一个动作，通过工具执行。
5. 工具等待游戏到达下一次可决策时刻，返回结果与新状态。
6. Codex 继续决策，直到胜利、失败、用户暂停或无法继续。
7. 用户可以随时接管；重新开始自动控制时，Codex 先读取实际状态。

首版可以由用户手动启动对局。角色选择和开局界面的自动操作在完整一局阶段逐步补齐。

## 3. 系统架构

```text
Codex 会话：观察、理解、选择下一步
              ↕ MCP 工具调用（STDIO）
本地 Python MCP 服务：协议转换、日志、错误处理
              ├─ 知识库与检索：实体规则、机制交互、策略资料
              ├─ 计算辅助：牌组统计、概率、候选变化对比
              ↕ 本地 HTTP / JSON
C# 游戏桥接模组：状态读取、动作校验、执行、结算检测
              ↕ 游戏正常动作流程
Slay the Spire 2
```

选择模组读取结构化数据作为主要路线。截图可用于诊断或核对，不承担首版的主要状态识别职责。

| 模块 | 建议技术 | 职责 |
|---|---|---|
| 游戏桥接 | C#，适配游戏当前运行时与模组加载方式 | 读取对象、执行动作、检测决策点 |
| 本地通信 | HTTP + JSON，绑定回环地址 | 提供可独立调试的游戏接口 |
| Codex 接入 | Python + MCP SDK，STDIO | 提供结构化工具 |
| 数据校验 | JSON Schema、Pydantic | 参数校验、字段约束、协议兼容 |
| 知识库与检索 | 首版 JSON / SQLite、实体索引与关键词标签；后期按需加入向量索引 | 提供有版本和来源的规则与参考资料 |
| 计算辅助 | Python 确定性计算模块 | 返回指标、假设与适用范围，供 Codex 判断 |
| 行动记录 | JSONL | 观察、动作、结果、错误的持久化记录 |
| 操作指南 | 项目 AGENTS.md，必要时封装为 skill | 约定游玩循环与恢复方式 |

模组的 .NET 目标版本、游戏类名、可用钩子、动作调用方式和 SDK 版本，在检查实际安装版本后确定。本规划中的接口名称均为拟定契约。

## 4. 各模块边界

### 4.1 游戏桥接模组

- StateReader：在游戏允许的线程上读取一致快照。
- ActionCatalog：枚举当前动作、参数、目标与选择限制。
- CommandExecutor：检查前置条件，调用游戏已有的动作入口。
- DecisionGate：识别结算、玩家选择、结束和未知状态。
- VersionAdapter：隔离容易随游戏更新变化的类名和调用方式。
- ControlGate：管理自动控制、暂停和人工接管。

网络线程接收请求并排队，不直接访问或修改游戏对象。读取与执行的线程调度方式需按游戏版本验证。

动作必须走正常游戏流程，使费用、触发效果、动画、统计和存档行为按游戏规则处理。不能通过直接改血量、金币或卡牌位置来替代正常操作。

### 4.2 MCP 服务

负责 MCP 与本地游戏协议之间的转换、连接检测、参数验证、日志和错误输出。游戏未启动时仍应能启动服务，并返回明确的未连接状态。

STDIO 标准输出仅承载 MCP 协议，调试日志写入标准错误或文件。第一版不额外建立调用模型 API 的调度进程。

### 4.3 Codex

Codex 根据当前信息选择动作，并在每个动作后重新观察。工具只判断是否可以执行，不替 Codex 选择“更优”动作。

可以记录简短策略理由，便于复盘；无需保存完整内部推理。

### 4.4 知识库与检索

知识库覆盖卡牌、升级效果、药水、遗物、状态、敌人规则、事件分支及机制交互。规则事实与策略建议分开保存，策略资料不作为执行权限或游戏规则。

首版使用实体 ID、名称别名、关键词和功能标签检索。get_reference 提供单实体查询，批量查询用于当前奖励及相关遗物。结构化资料可以直接检索后送给 Codex，不要求先搭建向量数据库或额外调用嵌入模型。

随着攻略、构筑分析和复盘资料增长，再按实际需求加入关键词与向量混合检索，将相关片段作为决策上下文。这是后续 RAG 扩展，不阻塞首版。

每条记录保存 entity_id、entity_type、适用游戏版本、语言、来源、更新时间、内容类别，以及已验证或待确认状态。策略资料额外注明适用角色、难度和前提条件。索引与缓存随资料版本更新。

当前实例的效果和合法动作以实时游戏状态为准；静态规则优先匹配当前版本；社区策略与复盘仅作为参考。资料冲突、版本不匹配或检索无结果时明确报告，不把未知补成事实。

事件决策优先读取当前页、动态选项描述和鼠标悬浮对应提示。无需在首次运行前逐个手工录入全部事件；知识库补充公开机制、概率、后续影响与策略经验，按事件/选项 ID 及游戏版本查询。提示缺失或特殊布局未适配时明确报告信息不足。

已导入的事件分支属于静态参考知识，应与未知随机结果区分：可以查询符合当前条件的公开规则与概率，不能读取本局尚未揭示的抽样结果。

### 4.5 计算辅助与构筑评估

计算层提供可解释的事实和指标，不自行抓牌、删牌或排序后自动执行。首版不建立统一的“卡组强度分数”。输出能力、格挡、费用、稳定性与成长空间之间的取舍由 Codex 判断。

逐步提供：

- 牌组统计：牌组大小、费用分布、基础牌占比、抽牌、能量、输出和防御等功能标签覆盖。
- 概率计算：在明确牌堆组成、抽牌数量与洗牌规则的条件下，计算关键牌出现概率。
- 候选对比：新增、删除或升级指定卡牌后的统计与概率变化；加入跳过或保持原状作为基线。
- 战斗计算：仅在支持的机制范围内计算伤害、格挡和费用，明确随机区间与不支持的交互。

功能标签只是提示，不等于实际战斗贡献。概率计算区分开局整副牌组与战斗中当前牌堆，并明确是否包含洗牌、额外抽牌或检索效果。

每次计算绑定输入状态版本，返回计算方法、假设、知识版本和限制。未知机制或条件不足时返回 unsupported / insufficient_data，不输出虚假的精确值。后期模拟器如有需要再独立规划。

### 4.6 抓牌、删牌与资源选择流程

1. 读取当前牌组、遗物、药水、血量、金币、地图和实际选项。
2. 查询候选实体与相关机制，优先获取当前版本规则。
3. 按需计算加牌、删牌、升级或保持原状的变化。
4. Codex 综合判断当前缺口、费用负担、协同、关键牌抽到概率、近期战斗与资源机会成本。
5. Codex 选择一个合法动作，执行前再次校验状态版本。

例如奖励决策必须考虑跳过；商店删牌需要与购买、保留金币和后续商店机会比较。计算工具不承诺未知未来战斗中的牌组胜率。

## 5. 游戏状态协议

每份状态快照应包含以下内容：

| 类别 | 主要字段 |
|---|---|
| 协议与身份 | schema_version、game_version、bridge_version、run_id、session_epoch |
| 状态标识 | state_version、phase、ready、control_mode |
| 玩家 | 血量、格挡、能量、金币、状态、遗物、药水 |
| 整局构筑 | 完整牌组及升级、角色、难度、章节、楼层、已公开地图与路线信息 |
| 战斗 | 手牌、牌堆可知信息、敌人、意图、回合信息 |
| 当前选择 | 选项、费用、目标、选择数量、可否跳过 |
| 合法动作 | 动作 ID、动作类型、合法目标、参数约束 |
| 最近结果 | 已执行动作、伤害、抽牌、状态变化、新的选择 |

状态版本表示与决策有关的状态变化，不按动画帧递增。run_id 标识当前局，session_epoch 区分桥接重启或重新加载，避免旧命令误用于新会话。

所有快照应在一致的游戏状态下生成；ready=false 时，Codex 不应提交新的游戏动作。

### 5.1 信息完整性

卡牌种类 ID 与卡牌实例 ID 分开，避免两张同名卡牌无法区分。敌人和选项也使用稳定实例标识，避免以列表位置执行操作。

卡牌描述和费用应反映当前升级、临时修改和战斗效果。基础数值、可计算结果和未知结果需要区分；不能把基础伤害直接作为最终伤害承诺。

默认暴露玩家能知道的信息。抽牌堆可以提供可知组成，未知顺序保持隐藏；不向 Codex 提供尚未揭示的随机结果或敌人未来决策。

### 5.2 控制输出大小

每次返回当前决策所需的完整摘要；重复的机制说明通过 get_reference 按需查询。近期变化可单独提供，但必须保留获取完整状态的能力。

完整快照可写入日志。不要每一步都把全部卡牌资料和整局历史发送给 Codex。

## 6. MCP 工具与动作契约

| 拟定工具 | 作用 |
|---|---|
| get_state() | 读取状态、连接情况和合法动作 |
| act(...) | 执行一个动作，返回结果或请求状态 |
| get_action_status(request_id) | 查询已提交动作是否完成 |
| get_history(...) | 按范围读取近期记录 |
| get_reference(entity_id) | 查询实体说明和机制信息 |
| lookup_entities(ids, ...) | 批量读取指定版本的实体资料与来源 |
| search_knowledge(query, filters, ...) | 按版本、类型和标签检索机制或策略资料 |
| analyze_deck(state_version, ...) | 返回牌组统计、功能覆盖和支持的概率指标 |
| compare_deck_changes(state_version, candidates, ...) | 对比指定加牌、删牌、升级与保持原状的指标变化 |
| set_control_mode(...) | 暂停、开启自动控制或交还人工操作 |

状态示例，省略了玩家和敌人的详细字段：

```json
{
  "schema_version": "1.0",
  "run_id": "run_001",
  "session_epoch": "session_a",
  "state_version": 42,
  "phase": "combat",
  "ready": true,
  "legal_actions": [
    {
      "action_id": "play_c17",
      "type": "play_card",
      "card_instance_id": "c17",
      "allowed_target_ids": ["enemy_2"]
    },
    {"action_id": "end_turn", "type": "end_turn"}
  ]
}
```

动作请求示例：

```json
{
  "request_id": "req_0008",
  "run_id": "run_001",
  "session_epoch": "session_a",
  "expected_state_version": 42,
  "action_id": "play_c17",
  "target_id": "enemy_2"
}
```

act 每次只接受一个有意义的游戏动作，不接受由本地程序自主决策的多步脚本。多选界面允许在一个选择动作中提交游戏要求的多个选项。

知识与计算工具为只读工具，按阶段开放。计算不修改游戏状态，不读取隐藏随机结果；候选集合由 Codex 或当前合法选项指定。概率与战斗计算的具体参数在支持机制明确后定义。

## 7. 执行与同步机制

命令生命周期建议为：received → validated → executing → completed / rejected / failed。接口同时表达当前是否到达决策点，避免将“收到请求”误认为“游戏已完成操作”。

执行规则：

1. 校验当前局、桥接会话、状态版本和控制模式。
2. 检查动作仍合法，参数和目标仍有效。
3. 同一游戏实例只允许一个修改命令处于执行中。
4. 调用正常游戏动作，等待下一次决策点或有界超时。
5. 保存执行结果，返回新状态及变化摘要。

### 7.1 重复请求与超时

同一 request_id 的相同请求返回已保存结果，不再次执行；相同 ID 但不同参数返回冲突错误。去重保留范围应在协议中说明。

超时可能发生在动作已经执行之后。Codex 或 MCP 服务先查询 get_action_status，不能直接换一个请求 ID 重发。

桥接重启后，如果无法确认未完成请求的结果，应返回结果未知并要求重新读取状态。不能宣称跨崩溃绝对保证恰好执行一次。

### 7.2 决策点与子选择

决策点包括正常玩家回合、奖励界面、地图节点，以及卡牌或药水触发的选牌、弃牌、目标选择等。

例如：出牌 → 选择弃牌 → Codex 提交选择 → 继续结算 → 返回战斗状态。所有子选择仍由 Codex 决定。

优先依据游戏动作队列和选择界面状态判断结算完成。固定延时仅作超时保护，不能作为主要同步机制。

### 7.3 错误与接管

建议错误类型包括 NOT_CONNECTED、VERSION_UNSUPPORTED、STALE_STATE、INVALID_ACTION、BUSY、CONTROL_PAUSED、UNKNOWN_PHASE 和 RESULT_UNKNOWN。

错误返回应说明是否已经执行、是否可重试，并在可能时附带最新状态。未知阶段暂停操作，保存诊断信息，不盲目点击。

用户暂停后停止提交新动作；已开始结算的动作正常完成。人工操作导致状态变化时，旧命令失效，恢复自动控制后重新获取状态。

## 8. Codex 会话与持续运行

正常循环为：读取状态 → 按需检索与计算 → Codex 决策 → 执行一个动作 → 检查结果 → 继续。

项目操作指南应约定每步重读、未知机制查询、禁止自动替代动作，以及用户暂停时的停止行为。

MCP 提供工具，不负责让已经结束的 Codex 会话自行再次开始。首版在活跃会话内持续游玩，受到会话、上下文和使用额度约束。自动恢复已结束会话如成为后续需求，需要单独验证 Codex 的运行与调度能力。

上下文恢复依靠游戏实际状态、近期行动和简短整局摘要。摘要记录牌组方向、路线计划和重要变化，不代替最新状态。

## 9. 日志、安全与版本维护

行动日志至少保存时间、局 ID、请求 ID、动作前后状态、提交参数、执行状态、耗时和错误。日志用于复盘和诊断，不保证精确重放；精确重放还依赖随机数、游戏版本与存档机制。

构筑决策还记录引用的资料 ID 与版本、计算输入和摘要结果，便于分辨问题来自资料过期、计算范围不足还是策略判断。复盘可沉淀为待审核知识，不能将单局结果直接当作通用规则。

本地游戏服务绑定 127.0.0.1，并使用本地凭据限制访问。接口只暴露明确的游戏能力，不提供任意代码执行或任意文件操作。游戏数据作为数据处理，不作为指令执行。

日志不保存访问凭据。需要测试时使用专门测试对局，并在确认存档行为后进行备份，避免诊断过程干扰正常进度。

启动时检测游戏、模组和协议版本。协议不兼容时拒绝操作；未知游戏版本先做只读验证。版本相关代码集中维护，避免散落在 MCP 层。

## 10. 开发阶段与验收

| 阶段 | 主要工作 | 验收标准 |
|---|---|---|
| P0：只读桥接 | 检查环境、加载模组、导出战斗状态、连接 MCP；确定实体 ID 与资料版本结构 | Codex 正确读出真实手牌、能量、敌人血量和意图；能关联实体资料 |
| P1：单场战斗 | 出牌、目标、结束回合、药水和子选择；命令校验与去重；当前实体的规则查询 | Codex 独立完成普通战斗；重复请求不重复执行；旧状态命令被拒绝；规则查询不混用版本 |
| P2：完整一局 | 奖励、地图、商店、休息、事件、开局与结束界面；牌组统计、候选变化对比与基础概率计算 | 指定角色与难度下，从开局持续操作到胜利或失败；抓删牌比较包含保持原状，计算返回假设与限制 |
| P3：恢复与接管 | 暂停、人工操作、断线、超时查询、摘要恢复 | 接管后可继续；响应丢失不重复动作；会话续接能恢复正确状态 |
| P4：扩展与体验 | 更多角色和机制、精简输出、诊断与复盘；按需扩展攻略混合检索和机制计算 | 提高覆盖范围与效率；资料可追溯；用实际决策问题检查检索质量，并通过多局验证 |

去重、过期状态拒绝和有界等待从 P1 就实现，P3 进一步完善故障恢复。

完整一局的验收不等同于保证通关或高胜率。可靠性先统计非法执行、重复执行、未覆盖界面和无法恢复的中断；策略效果再用多局样本评价。

## 11. 测试计划

- 协议测试：字段约束、非法目标、重复请求、冲突请求和过期版本。
- 状态测试：两张同名卡牌、临时费用、敌人死亡、选项变化和快照一致性。
- 流程测试：出牌后抽牌、嵌套选牌、战斗结束奖励和事件多阶段选择。
- 故障测试：响应丢失、游戏关闭、桥接重启、暂停和人工接管。
- 游戏内验证：对照界面核对导出状态，确认每条命令走正常规则流程。
- 知识测试：实体别名、版本过滤、来源追溯、资料冲突、检索无结果和过期缓存。
- 计算测试：用可手算的小牌组核对概率，验证加删牌与升级对比；条件不足或机制不支持时明确返回限制。
- 构筑场景验证：检查抓牌、跳过、删牌和保留资源是否都能参与比较；用代表性问题核查返回资料的相关性与覆盖率。

无需训练模型或先写完整游戏模拟器。测试重点是桥接正确性、连续操作可靠性，以及知识和计算结果是否准确、可追溯。

## 13. 开始前需要确认的事项

| 待确认项 | 用途 |
|---|---|

| 正常动作入口与结算状态 | 确认桥接技术路线可行 |
| 模组对存档、进度和成就的影响 | 确定测试方式与安装说明 |
