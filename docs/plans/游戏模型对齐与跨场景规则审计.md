## 1. 根因和目标

前期将“移除兼容层”错误地扩大为“实体效果全部写进 Python 注册表”。这使基础数据、效果定义、文案解析及场景专用计算成为多套规则来源。即使单个实体的数值正确，跨场景触发、获得物品后的状态变化和效果顺序仍可能不一致。

游戏自身采用模型类、DynamicVars、公共命令、Power/Relic 等模型的生命周期钩子和状态机。游戏并非从当前导出的百科 JSON 执行效果。我们应按这一语义结构建立模型，并用标准 JSON 承载实体参数与效果引用，由现有核心代码实现公共机制。

统一目标：**基础数据和实体定义 → 公共命令与生命周期 → 状态变化 → 各场景策略评估**。

- 同一实体只有一份权威定义；游戏导出的数值被直接引用，不在场景代码中再次填写。
- JSON 声明已有机制的组合、条件、目标、顺序、升级规则和状态字段；调整数值或组合时只改数据。
- 核心代码实现伤害、治疗、获得/移除、能力施加等公共机制。真正的新机制需要补充核心实现及《机制大全》，随后由 JSON 引用。
- 新定义直接成为核心模型的数据来源，不再叠加兼容注册表、旧路径回退或另一套审批执行层。
- 策略评估可以使用启发式权重和不确定情景，但不能另外解释游戏效果。

## 5. 标准模型需要包含的内容

所有场景采用同一模型引用和命令语义；不要求所有场景拥有同样的状态机或字段。

1. **身份和基础数据**：稳定 model ID、类别、来源版本、费用、目标类型、关键词、池、稀有度、升级规则；复用已有拉取结果。
2. **变量**：名称、类型、BaseValue 及必要的 Props；区分基础值、附魔值、显示预览值和实例当前值。
3. **效果绑定**：命令/能力/其他模型引用、参数表达式、目标、执行顺序、条件和重复次数。实际效果引用独立于变量名称。
4. **生命周期**：触发点、所有者与来源、监听范围、修正阶段及顺序、一次性/每回合状态和重置时机。
5. **状态与流程**：事件页面、怪物动作、房间选项、商店库存及价格修正；显式状态转换、分支条件和有依据的随机权重。
6. **选择和随机边界**：目的、候选来源/过滤、数量、可取消/确认方式、后续操作；未观测的抽牌或随机结果以分支或未知表达。

效果回调包含任意 C# 逻辑，不能仅凭反射导出变量就自动获得完整可执行 JSON。结构化定义需要逐项对齐源码语义，公共机制在核心代码实现一次；不能继续把正则识别源码或文案当成运行时执行依据。

## 6. 实施顺序与验收

1. 确立统一模型结构、命令与钩子契约；扩展基础导出并建立完整类型和模型引用。先覆盖 FlexPotion、Permafrost 等能揭示差异的实体，验证数据修改确实驱动执行。
2. 将当前实体注册定义迁入权威 JSON；让现有核心直接读取，去除旧实体定义、文案执行及兼容回退。缺失的结构化效果应明确报未覆盖。
3. 补齐跨场景 RunState 及获得、移除、升级、治疗、支付等公共命令；使商店、奖励、事件、宝箱共用状态迁移，保留策略各自的评估方式。
4. 迁移事件/先古与怪物状态机，补齐休息选项、特殊奖励和选牌来源语义；移除运行时源码表达式解释路径。
5. 清点全量实体和场景的定义及交互覆盖，校准策略，核对真实动作前后的公开状态。

验收重点：

- 相同命令无论来自卡牌、事件、商店还是奖励，都遵循同一状态迁移和钩子顺序。
- 修改已有变量或已有机制组合的 JSON 后，无需编辑 Python 即可改变预测；新增机制同时有核心实现和机制文档。
- 可用相同起始状态对照游戏与预测的命令轨迹和公开结果；包括临时能力、一次性状态、获得效果、价格变化、多张升级等交互。
- 全量报告区分“基础数据存在”“效果定义完整”“公共机制支持”“交互已验证”，不再以实体 ID 登记数量表示全部完成。
- 所有场景的缺失规则保持可见；源码证据和文案仅用于审计、展示及说明，不再参与状态执行。

此前记录的 311/961 实体已定义仅表示旧实现的登记覆盖，不是新架构的完成比例。

## 8. 不允许再次走偏的实施约束

1. **按实际调用理解效果。** 变量类型、变量名、显示文案、预览数值都不能代替 OnPlay/OnUse/OnChosen 与钩子中的真实调用。
2. **规则直接进入核心。** 可以给现有核心增加模型加载、校验和命令处理能力；不能再在外面套一层实体映射、兼容修补器或另一个专门服务。
3. **同一效果只有一个执行定义。** 场景差异用来源、条件、目标和上下文表达；不能分别实现“商店版获得遗物”和“事件版获得遗物”。
4. **数据确实控制行为。** 将 Python 原样字符串搬进 JSON 后再执行，或让 JSON 仅保存 entity_id 再跳回逐实体 if/else，均不算完成。
5. **表达式和控制流要明确。** 使用有限、可校验的操作和表达式，不在 JSON 中放任意 Python/C# 脚本，不用 eval 执行源码。公共机制仍由核心代码提供。
6. **源数据和语义分工清楚。** 已导出的事实直接引用；缺失的调用、条件、状态语义按游戏源码补全。可保留原始导出和规范模型两个文件集合，但每个事实或效果只能有一个权威来源，核心加载后只有一套生效定义。
7. **不能伪造规则或概率。** 未知参数、隐藏抽牌顺序、尚未公开的奖励等保持未知或有依据的分布；游戏模型完整不等于拥有未来信息。
8. **保留顺序和实例身份。** 数值精度、取整时机、命令先后、监听顺序、所有者、来源、牌/药水实例及可变计数必须明确。
9. **不以零或罚分掩盖缺口。** 缺少规则时给出未覆盖模型/机制和受影响结果；启发式估值可保留，但不能伪装成精确状态转移。
10. **模型定义与执行权限分开。** 保留已有合法性、新鲜度、观察边界和实际动作校验，不重新建立逐实体批准制度。
11. **尊重当前工作区。** 当前有大量已有修改。开始前检查 git status；不 reset/覆盖无关变更，不恢复用户删除的工作流，不擅自提交、发布、部署或控制游戏。

## 12. 验证方法和本地执行入口

### 12.1 验证分层

1. **结构与引用校验**：全数据 schema、引用闭合、参数/状态作用域/升级规则有效；错误定位明确。
2. **机制语义测试**：检验命令、前后钩子、顺序、边界和交互。不能只断言 JSON 中存在某个字段或 ID。
3. **数据驱动测试**：修改测试用 JSON 数值和已知机制组合，重新加载后验证行为改变、缓存失效，且不改核心实体代码。
4. **全目录审核**：每个模型及升级/难度变体的完整性和机制依赖；代表交互、边界和状态机轨迹另测。参数绑定通过不代表所有组合都已验证。
5. **跨场景与默认入口测试**：从统一决策/实际生产调用链验证相同模型生效；候选互不污染；动作引用、新鲜度和观察边界不回退。
6. **游戏语义对照**：在可控相同状态和选择下，比较命令轨迹及公开结果；无法获得轨迹时说明仅比较了哪些结果。
7. **战略/搜索实验**：固定价值/风险版本、输入、预算和种子，分别测规则、分布、价值和搜索误差，不以启发式分数上升证明胜率上升。
