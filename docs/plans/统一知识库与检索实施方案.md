# 统一知识库与检索实施方案

日期：2026-10-14。状态：已实施首版统一读取、目录命名、本地检索和审核经验发布；实际功能与边界见 [使用说明](../reference/统一知识库使用说明.md)。版本目录迁移、多数据集事务发布和完整质量评测仍是后续规划。根据用户最新决定，本期只建设无模型知识库，不接入 embedding、rerank 或向量数据库。

## 1. 建议结论

先建设统一知识访问层，复用现有游戏资料和验证规则，再建设实体索引、别名、SQLite FTS 关键词检索及显式关系查询。本期不引入 Chroma、pgvector、embedding、rerank，也不实现模型配置、凭据管理或模型专用适配器。

目标是：业务模块不再自己定位和解析知识文件；每次决策使用同一个知识修订；事实、规则、经验有明确来源；所有索引可从统一原始资料重建。

统一知识库不意味着所有资料塞进一个文件，也不意味着所有数值通过向量检索获得。保留按实体、机制、规则、经验划分的数据集，由统一服务管理读取、校验、缓存、版本、关联和检索。

## 2. 实际代码问题

本次检查确认主源码和资料中有三个承担不同职责的 knowledge 目录：

| 当前位置 | 实际职责 | 建议 |
| --- | --- | --- |
| `data/knowledge/` | 百科、行为、机制、规则、图片及本机生成资料 | 保留为唯一知识原始资料根目录 |
| `src/python/src/autoslay/knowledge/` | 数据加载、查询、导出支持和来源解析代码 | 重构并改名为 `autoslay.knowledge_base` |
| `src/python/tools/knowledge/` | 导出、审计、修复等维护脚本 | 改名为 `tools/kb_admin/` |

这里的三个是主源码范围的核查结果，不是整个工作区绝无第四个目录的断言。迁移前应另行盘点忽略目录、缓存、旧副本及空目录，给每项标记为正式资料、代码、缓存、测试夹具或历史备份；测试夹具和缓存不参与正式资料发现。

代码目录叫 knowledge 并非技术错误；改名主要解决“哪些是资料、哪些是实现”的歧义。更关键的问题是以下读取职责已经散落：

| 文件 | 当前行为 | 重构方向 |
| --- | --- | --- |
| `agent/context.py` | 每次构造上下文直接读取百科 JSON | 批量调用实体查询及上下文组装接口 |
| `dashboard/server.py` | 直接读取百科、怪物图片索引、覆盖资料 | 调用分页浏览、资源和审计接口 |

| `rules/periodic_relics.py` | 直接读取规则文件 | 使用同一知识快照的规则视图 |
| `knowledge/catalog.py` | 每次构造 Catalog 都解析文件 | 接入共享仓库和实体索引 |
| `knowledge/behavior.py` | load 每次读取行为文件 | 接入共享仓库和行为索引 |

已有资产应复用：百科校验、规则指纹、来源审计、游戏程序集校验、原子更新和历史备份都已经存在。此次重构不能为了统一接口而绕过这些验证。

当前 `data/knowledge/` 已有 catalog、behavior、mechanics、rules、events、assets、coverage 七类资料。递归统计包含历史文件，不能把目录体积或文件数直接当成活跃知识量；构建索引必须按清单选择当前有效资料。

## 3. 知识范围与目录

建议最终目录如下。为降低风险，第一阶段保留已有内部路径，待调用收口后再迁移为版本目录。

```text
data/knowledge/                         唯一知识原始资料根目录
  manifest.json                        活跃修订、数据集位置、哈希和依赖
  versions/<build-id>/<language>/
    catalog/                           卡牌、药水、遗物与分类
    behavior/                          怪物、意图、事件行为、关联状态
    mechanics/                         游戏机制说明和实体关系
    rules/                             验证过的规则与确定性证书
    assets/                            图片和资源索引
  experience/
    timing/                            经审核的耗时统计与适用环境
    strategy/                          经审核的策略经验
  staging/                             待校验导入、待审核经验与规则提案
  history/                             旧修订；默认不检索

src/python/src/autoslay/knowledge_base/  统一知识服务与存储、检索实现
src/python/tools/kb_admin/              知识维护命令
config/knowledge.default.json           检索权重、过滤条件、缓存与上下文预算
.runtime/local/knowledge/              本机知识配置覆盖
.runtime/cache/knowledge/              可删除、可重建的索引
  <revision>/lexical.sqlite
data/runs/                             原始对局证据，仍由归档系统管理
data/calibration/                      原始校准记录，仍由校准系统管理
.runtime/logs/                         原始运行耗时与诊断日志
docs/                                  项目设计文档，不默认混入游戏知识
```

build-id 包含游戏版本和程序集哈希标识；不能仅靠显示版本判断相同构建。策略和耗时经验可以跨版本，但必须声明适用范围；规则、行为和精确数值必须绑定具体构建。

JSON/Markdown 是可审计的原始资料；SQLite 是派生索引。避免让数据库成为另一份需要手动维护的知识真相。Git 可发布规则与机制；本机游戏导出、图片、历史、经验中的私有证据和索引继续按现有发布策略处理。

### 时间数据如何归类

| 时间信息 | 归属与读取方式 |
| --- | --- |
| 遗物每 N 回合触发、增益持续回合 | 游戏规则/机制，由知识服务提供 |
| 实测动作稳定耗时、阶段 p50/p95 | 原始日志由 telemetry 保留；审核后的聚合进入 experience/timing |
| 模型与网络延迟 | 与 provider、模型、环境和采样时间绑定，作为统计经验 |
| 搜索预算、请求超时、轮询间隔 | 运维/策略配置，仍由配置系统管理 |
| 当前动作进行了多久、当前回合计数 | 实时状态，不作为静态知识 |

例如现有 `shop_time_ms` 是搜索预算，不能搬成游戏机制；`report_timing.py` 得出的统计可以成为候选经验，但不能把未测量的阶段归因给模型或动画。每条耗时经验至少包含 measurement_scope、单位、样本数、p50/p95、采样区间、环境、版本和证据引用；环境不符或样本不足返回缺口。

## 4. 统一访问设计

```text
Agent / 决策与规则 / MCP / 观察台
                 |
           KnowledgeService
                 |
     KnowledgeSnapshot + 领域视图
                 |
      Repository / DatasetLoader
                 |
  manifest + 原始资料 + 派生索引
```

公开接口建议：

```python
snapshot = kb.acquire_snapshot(build=build, language="zh-CN")
kb.get_entities(ids, snapshot=snapshot)
kb.get_mechanics(ids_or_tags, snapshot=snapshot)
kb.get_monster(entity_id, ascension=level, snapshot=snapshot)
kb.get_rule_view(snapshot=snapshot)
kb.get_timing_profile(scope, environment, snapshot=snapshot)
kb.search(query, filters=filters, mode="lexical", limit=10,
          snapshot=snapshot)
kb.build_context(visible_state, budget=budget, snapshot=snapshot)
kb.status()
```

这些是拟定接口，不是当前已实现 API。怪物接口只返回已验证的行为和可解析数值，不承诺任意源码表达式可求值；保留现有 unresolved/unsupported 行为。

服务统一管理文件访问；实体、机制、规则、经验各自有类型化接口，避免形成一个无边界的巨型类。图片由资源接口提供受控路径/字节流；目录浏览和规则计算直接使用类型化接口。

### 缓存与进程边界

1. 每个常驻进程通过工厂获取共享 Repository；同一进程、同一修订、同一数据集只加载解析一次，按需加载大数据集。
2. Repository 缓存不可变对象；对现有会修改字典的调用提供副本或只读领域视图，避免调用污染共享知识。
3. 一次决策显式绑定 KnowledgeSnapshot，传给 normalize、RuleRegistry、MonsterRules、mechanisms、Agent 上下文；不能各模块自行取“最新”。
4. 更新成功才切换活跃修订；进行中的决策继续用旧修订。旧快照引用释放后才能回收其缓存。
5. 文件 mtime/size 可用于快速检测，但发布一致性以 manifest 修订和内容哈希为准。保留有限旧修订和有容量上限的缓存。

Python 单例只在一个进程内共享。MCP、常驻执行器、观察台若分别启动，不会共享同一份内存。这些进程仍应调用同一套 KnowledgeService，并绑定相同修订。首版每进程各有缓存，比增加 IPC 更易维护。

如果测量证明确实需要跨进程只加载一次，再让已有常驻服务承载知识服务，其他进程经本地 RPC 请求。避免首版创建独立微服务；若用户要求全进程零重复解析，则应直接采用该 RPC 方案，并增加服务启动、超时和不可用测试。

### 返回与缺口

检索结果统一携带 knowledge_id、entity_ids、dataset、revision、game_version、assembly_hash、language、source_ref、content_hash、review_status、compatibility 和 applicable_conditions。

精确计算遇到构建失配、规则未审核、证据不足时返回结构化错误；允许解释性的旧资料必须显式标记，不自动进入规则视图。检索分数只是排序分数，不是事实可信度。可信度按来源和审核状态表达。

当前可见游戏状态优先于静态默认值；随机未揭示结果不能从资料中推断为已发生。继续保留“参考覆盖不等于模拟支持”的现有边界。

## 5. 无模型检索方案

首版推荐 SQLite + FTS5，配合 Python 内存中的实体 ID 索引、别名表和显式关系表。SQLite 可使用标准库；需先确认项目 Python 构建提供 FTS5，不提供时选择兼容实现或回退到内存关键词索引。

检索流程：

1. 先按构建、语言、资料类别、审核状态、适用条件筛选。
2. 识别实体 ID、准确名称和别名，直接返回精确命中；规则计算只走这条路径。
3. 自然语言查询采用关键词检索，分别给名称、别名、标签、机制标题和正文加权。
4. 按显式实体关系补充关联资料，例如怪物→意图→状态效果、遗物→触发机制；限制关系深度和条数。
5. 按查询相关性、兼容性与来源优先级排序，合并重复资料，并在上下文预算内返回证据。

中文不能只使用默认按空格分词。建议首版建立中文相邻二字词索引，保留英文词、ID 和数字；短名称、单字及实体别名另设精确/前缀匹配。用项目查询集评估后再决定是否增加中文分词依赖。自然语言无结果时明确返回缺口，不用不相关条目凑数。

这里实现的是 FTS/BM25 及规则排序基线，不调用远程 rerank 模型。别名优先由游戏本地化和人工配置提供，避免用模型自动生成事实。

## 6. 本期范围与配置

检索全部在本地完成，不需要模型 key、外部 API、模型下载或向量数据库。排序采用精确命中优先、FTS/BM25、字段权重、兼容性和来源规则。

配置包含检索结果上限、字段权重、关系扩展深度、缓存容量、上下文预算和版本过滤策略。统一 search 接口保持业务与检索实现解耦，但本期不为未来模型接入增加专用抽象或空实现。

经验审核、耗时画像和来源追踪继续实施，它们不依赖向量化或排序模型。

## 7. 更新与知识沉淀

导出/导入 → staging → schema/来源/构建校验 → 实体与规则依赖检查 → 生成 manifest 和差异报告 → 原子发布修订 → 后台更新索引 → 发布索引状态。

第一阶段兼容当前单文件原子更新；最终多数据集更新使用不可变修订目录加活跃 manifest 原子切换。不能用逐个替换文件的方式宣称获得跨数据集一致性。

规则指纹必须基于原始事实，不基于检索文本；关键词索引变化不应影响规则审核。删除条目同时删除派生索引，改动只重建变化的检索记录。索引更新失败不撤销正确的原始资料修订；搜索返回明确的索引落后状态，必要时使用同一快照的内存关键词回退，精确实体查询继续可用。

实战记录保留在原归档位置。经验候选引用 run_id、decision_id、snapshot_ref 或日志区间；去掉实时隐藏信息，声明条件和反例，审核通过后才发布为经验。现有 events/observations 属于原始观察，后续迁入归档/证据层并保留迁移映射，不能直接作为正式事件规则。

知识服务不默认索引整个 docs 目录；项目设计文档需要另建 project_docs 命名空间，与 game 查询隔离。这样能在一个资料管理体系下扩展范围，避免设计讨论被当成游戏事实。

## 8. 分阶段实施与验收

| 阶段 | 具体交付 | 验收条件 |
| --- | --- | --- |
| A：盘点与统一读取 | 数据集清单、Repository、Snapshot、Service；迁移已有读路径 | 业务模块不直接读知识 JSON；同进程未变数据只解析一次；原功能等价 |
| B：命名和资料归位 | knowledge_base/kb_admin；版本清单；经验和原始观察分类；更新文档、工具路径及忽略规则 | 导出、刷新、回滚、启动脚本和发布包无路径遗漏；旧资料可追溯 |
| C：无模型知识检索 | SQLite FTS、别名、关系、统一 search/context；MCP 和观察台接入 | 无 key 完整运行，中文查询与精确实体查询通过评测 |
| D：经验发布与耗时画像 | 经验审核流程、条件过滤、证据引用、耗时聚合查询 | 来源可追踪；环境失配与样本不足明确返回缺口；原始观察不自动升级为规则 |

实施时先收口 I/O，再改名和迁移物理位置，避免路径迁移与读取语义变化同时扩大排查范围。旧公开模块/工具可保留一个迁移阶段的转发入口；转发必须调用新实现，不能再复制加载逻辑。更新所有 Python import、PowerShell/启动命令、README、设计文档和 CI。

旧 MCP query_encyclopedia、query_behavior_log、query_game_mechanics、audit_knowledge_rules 保留兼容入口，内部统一调用服务；新增 search_knowledge 和 knowledge_status。前端仍可提供按类别浏览、版本/来源详情、缺口与索引状态，保持现有按类别浏览的使用方式。

### 质量与收益评测

固定一套建议至少 100 条的查询集，包含实体 ID、中文别名、跨语言表达、机制组合、怪物进阶、策略经验、时间画像、过期版本和无答案问题。每条标注所需知识 ID、适用构建、可接受答案/引用和应拒绝的旧资料。

按查询类型对比现有查询与新无模型检索：实体准确率、Recall@5、nDCG@10、无答案误召回、错误版本比例、上下文大小、冷启动与热查询 p50/p95。检索质量之外再检查生成解释是否引用正确证据，避免高召回掩盖不可靠答案。

验收要求：精确实体查询不得退化，精确计算错误版本使用为零；自然语言查询的召回与排序应优于现有简单子串检索，并满足明确的延迟与上下文预算。评测前冻结查询集与目标，保留无答案和短中文名称等边界用例，不把未经实测的提升当作已实现效果。

必须验证的场景：并发读取与刷新、调用方修改返回值、更新中断、构建不匹配、快照跨模块一致、删除后无旧检索命中、索引损坏重建、FTS5 不可用时的回退、多进程读写以及回滚后依赖规则的兼容性。运行现有知识、行为、怪物模拟、事件、规则、Agent 上下文及观察台回归；本机导出资料测试与可移植测试分开。

实施后记录决策报告中的 knowledge_revision、引用知识 ID 和检索模式，让复盘能区分资料问题、检索问题和计算问题。缓存命中、解析次数、加载耗时与索引修订差距作为诊断指标，不向日常用户流程暴露实现细节。

## 9. 优先顺序

按 A、B、C、D 实施，获得统一、离线可用、可追溯的知识库，并支持审核后的策略经验和耗时画像。后续若检索评测发现明确不足，再另行评估改进方法。

本期优先完成统一数据访问、同次决策的一致性、来源与版本管理、中文别名和实体关系。这些能力直接影响结构化游戏资料的正确使用，也是无模型检索的基础。
