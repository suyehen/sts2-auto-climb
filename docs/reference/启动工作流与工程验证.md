# 启动工作流与工程验证

## 分层与入口

工作台默认入口为「开始游玩」，其后为实时观察、对局记录、Agent 管理与百科。`play.js` 负责表单与轮询，`play-state.js` 只负责把公开状态投影为按钮条件和人类可读说明。页面不直接向游戏提交动作。

浏览器经工作台服务访问 `/api/play/state`（读取）和 `/api/play/start`（提交启动任务）。工作台沿用本机 Host／Origin 防护，Agent 服务沿用令牌认证。启动请求包含唯一请求编号、模式、后端、职业与进阶；进阶 `null` 表示选中职业后读取游戏实际已解锁上限，不写死最高难度。

`agent/launch.py` 独立协调 Steam 启动、等待桥接、菜单选择及 Agent 接管。运行循环和模型适配器继续各自独立。任务立即返回，通过状态轮询查看进度；不占用一个长 HTTP 请求等待游戏启动。Steam 可从当前安装目录或 Windows 安装注册表定位。

## 状态与保护

正常路径：检查 → 启动／等待游戏 → 续档或设置新局 → 启动 Agent → 完成。取消、失败和服务中断均有独立状态；Agent 服务启动时保持暂停，重启不自动恢复游玩。

已结束对局的结算页面会通过游戏已有的继续结算／返回主菜单接口正常离开，然后进入所选启动流程。

- 未指定角色时使用铁甲战士。角色是否解锁、指定进阶是否可用，由游戏菜单实际数据验证；无效设置停止流程。
- 续档在主菜单执行 `continue_game`；当前正在对局中时直接接管。新局在当前对局中会拒绝，要求先保存返回主菜单。
- 有存档时默认阻止新局。用户明确勾选放弃旧存档才允许调用游戏的正常放弃接口；确认附带当前会话与状态版本，变化后需重新确认。放弃不可撤销，后续角色或进阶校验失败不会自动恢复旧存档。
- 菜单操作与现有执行器共用进程间派发锁；每个动作在提交之前写入请求日志。重复启动请求使用同一编号返回已有记录，参数冲突会拒绝。
- 超时或取消时已提交的游戏操作不能撤回。日志没有确定结果时，只查原请求状态；新启动以及直接接管都会检查未确认动作，不盲目重发。
- 浏览器暂时断线保留启动编号，恢复后先查询该编号；若服务确认没有记录，才重试同一启动请求。关闭页面不会暂停后台任务。

启动日志为 `.runtime/logs/agent/launch/<request_id>.json`，只保留本机运行记录，不进入业务配置导出与 Git 仓库。首页工程视图可以查看公开启动状态、原始菜单数据与步骤结果。

## 验证方法

后端生命周期测试使用模拟桥接：覆盖默认最高进阶、自定义进阶、续档、当前局接管、存档确认过期、重复编号、启动期间重复点击、未知结果阻止后续动作、取消与服务重启恢复、配置前置验证及连接超时。HTTP 测试验证防护、请求编号透传与静态资源。前端状态测试覆盖按钮条件、离线启动入口与可读阶段说明。

浏览器验收检查默认导航、表单、进阶切换、存档提示、普通／工程视图、窄屏排版及状态轮询。真实菜单读取可以验证数据兼容性；模拟测试通过不等于真实游戏完整启动闭环已实测。

开发验证保持 Agent 暂停，不为测试放弃现有存档。需要真实闭环时，用户从首页选择新局或续档，即授权对应操作以及进入自动游玩。

2026-10-12 验证：完整 Python 回归 348 通过、5 失败；五项在修改前的工作台服务代码下同样复现。四项涉及本地遗物资料指纹失配（FIDDLE、HAPPY_FLOWER、PENDULUM、BURNING_BLOOD），一项是旧回放状态轨迹断言。启动生命周期、配置和 HTTP 的独立回归通过；本次没有放宽指纹校验或改写计算规则来消除失败。

最终相关 Python 回归 62 项通过，前端 32 项通过。浏览器检查了默认导航、自定义进阶切换、字段名称、普通／工程视图以及 720 和 1280 像素视口，均无横向溢出。部署后只读核实：游戏仍在主菜单、现有存档存在、Agent 与启动任务均未运行。真实游戏新局／续档到模型决策的完整闭环尚未在本次改动后实测。

后续战斗修复已解决上文五项遗留失败，最新完整回归为 377 项通过。具体兼容证明、怪物规则和验证范围见《战斗推演与怪物规则》。
