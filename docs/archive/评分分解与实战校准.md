## 基础价值、配合与环境

卡牌具有独立的资源描述：伤害、格挡、抽牌、能量、力量、费用及代价。`intrinsic` 提供中性环境下的单牌资源换算，费用单独列出；它不是脱离卡组的强度排名。

牌组总分拆成五部分，所有分项之和等于总分：

```text
V(卡组,环境) = 基础资源价值 + 卡组配合修正 + 环境修正 + 规则约束修正 + 代价
选牌收益 = V(加入后,环境) - V(加入前,环境)
```

因此选牌不能只用“这张牌自身得几分”。加入一张牌也改变抽到其他牌的概率、能量需求和配合密度。删牌、升级和商店组合调用相同的牌组估值，报告给出 `component_deltas`，方便查看边际收益来自哪里。

| 分项 | 当前实现 | 独立配置 |
|---|---|---|
| 基础资源价值 | 中性环境的伤害、格挡、抽牌、能量、力量、易伤 | `run.default.json` |
| 卡组配合 | 力量与攻击密度／多段攻击，抽牌与零费牌密度，消耗非攻击牌的格挡收益 | `context.default.json` |
| 环境修正 | 低血量与精英／首领压力、多敌人群伤、易伤受益攻击密度 | 环境输入与基础权重 |
| 规则约束 | 禁止效果抽牌、手牌上限、调用方提供的可抽牌数量上限 | 事实约束，不靠调权重解除 |
| 代价 | 诅咒／状态负担、自损 HP、牌组膨胀；商店另列金币机会成本 | 基础与配合配置 |

抽牌规则先决定可产生多少实际效果。例如单次抽 3：禁止效果抽牌时为 0；出牌后手里已有 9 张时，容量最多允许 1 张；可抽牌总量明确只有 2 张时，最多为 2。只取消抽牌分量，保留牌上其他效果。由于牌组评估不是即时战斗模拟，默认用开局手牌减一作为出牌后容量假设，报告公开该假设；可通过 `expected_hand_after_play`、`expected_draw_available` 提供更具体的情景。

FIDDLE 的禁止效果抽牌由真实遗物状态识别；战斗内可见 NoDraw 状态也会阻止效果抽牌。调用方无法用 `draw_blocked=false` 解除已经读到的禁止状态。下一回合正常抽牌与效果抽牌的差别仍由已有战斗机制模块处理。

配合目前是有界代理估值，不是完整组合模拟。力量先后顺序、所有消耗触发、所有遗物与卡牌配合仍需要专属规则。未知卡牌单牌价值为未估值，未知卡组贡献列在 `unknown_cards`；已知分量总分不能代表完整卡组强度。报告状态继续为 `uncalibrated`。

## 解耦与更新

- `evaluation/run.py`：资源提取、基础权重、单牌描述与改变前后比较。
- `evaluation/contextual.py`：配合、环境、规则约束及评分分解。
- `calibration/store.py`：分析、选择意图和观察结果的独立存储。
- `calibration/report.py`：样本、预测误差和按版本／策略／角色／进阶分组的诊断。
- `calibration/tuning.py`：离线比较候选权重配置。
- `config/decision/context.default.json`：配合系数，与基础资源权重分开维护。
- `config/decision/calibration-profiles.json`：待比较的参数组合，不是已校准的有效策略。

配置内容、配合模块版本、游戏版本和百科哈希进入分析缓存键，更新后不会复用旧权重报告。服务代码更新需重启常驻服务。不同模块可以独立改动与回归。

## 实战证据如何收集

通过 MCP `analyze_decision` 或常驻服务 `/decision` 获取报告时，会自动归档至 `data/calibration/analyses/`。只保存公开游戏数据、报告与配置来源，不保存桥接令牌；也不会把整个百科送入上下文。离线计算器与回放不会自动写入实战校准库。

Codex 选定方案后、执行前，调用：

```text
record_decision_choice(
  analysis_id=报告ID,
  group="choices", index=报告中的候选下标,
  reason="配合收益／环境修正及风险理由",
  trial_id="同一完整对局的稳定标识"
)
```

`group` 支持 `shortlist`、`observations`、`choices`、`shop`、`event`、`route`、`rest`、`combat.candidates` 等。必须使用当前报告内的下标，不是重新排序后的下标。状态版本、会话及状态哈希必须仍匹配。一个分析 ID 只能记录一种选择；重复相同请求不增加样本。

这是选择意图，不执行游戏，也不证明已经执行。执行继续使用已有的 `act`、`execute_plan` 等接口，先检查新鲜合法动作。到了实际动作、回合、战斗或整局的观察终点，调用：

```text
observe_decision_result(decision_id=原分析ID, horizon="turn", note="已执行所选前缀并结束回合；记录实际新回合状态")
```

`horizon` 为 `action/turn/combat/run`。整局标签可指定 `trial_result="win/loss/abandoned"`，但明确标为调用方报告，不冒充游戏自动验证。相互矛盾的终局标签会被排除。重启后的跨会话数据须显式复核导入，不能自动把另一局的结果关联过来；同一局使用稳定 trial ID，避免重启后误算为多个样本。

当前桥接没有公开种子字段，记录为未知，不声称已做相同种子的配对实验。按游戏版本、策略内容、角色和进阶分组统计；对局中途改权重会标成混合策略局，并排除其策略胜率估计。

常驻服务对应 `/calibration/choice` 与 `/calibration/observe`。客户端可使用 `execution_client.py calibration-choice 文件.json` 和 `calibration-observe 文件.json`。若当前 MCP 工具列表尚未更新，可先用常驻服务入口，重载 MCP 后显示两个新工具。

## 如何调整权重

先做数值正确性诊断。动作预测与实际结果的偏差优先检查规则；回合 HP 差额可能包含回血、额外动作或未知钩子，不能直接归因于选中的某张牌。启发式分数和 HP 单位不同，也不能简单把“分数减实际损血”当误差。

再比较策略。候选评分配置先离线运行，并用独立复核的排序标签检查是否改善判断。`calibrate_scores.py` 支持 JSONL 标签，例如：

```json
{"analysis_id":"已归档的报告ID","trial_id":"run-001","group":"choices","preferred_index":1,"other_index":0,"label_source":"human_review"}
```

标签必须来自 `human_review` 或基于实际配对结果的 `paired_trial_review`；计算器自己选的方案不当作训练真值。重复标签只计一次，冲突标签全部排除。当前离线参数比较器只比较已支持卡牌的选牌／删牌／升级，不把有未知卡的完整强度当真值。

调参集与验证集用整局标识稳定分开，比例约 80/20，按每局平均符合度评分，避免长对局权重过大。同一个物理会话／对局被取了多个 trial ID 时会拒绝比较，防止数据泄漏。初始筛选至少 10 个调参局和 5 个验证局，且验证集比基线好，才生成待审方案；这个门槛不是统计显著性的证明。脚本始终 `applied=false`，不会修改当前配置。

之后还要在新的独立实战对局比较基线与候选方案，控制角色、进阶、游戏版本、Codex 决策流程与预算。观察通关／存活、损血、资源使用和耗时，不能根据一局的输赢归因某张牌。按组报告已标注整局的胜率和近似 Wilson 区间；小样本区间会很宽，未控制种子的差异仍可能来自局面难度。

运行：

```powershell
& .runtime/conda/python.exe src/python/tools/analysis/calibrate_scores.py
& .runtime/conda/python.exe src/python/tools/analysis/calibrate_scores.py --labels data/calibration/reviewed-pairs.jsonl
```

第二条仅在标签文件实际存在时运行。没有足够样本或验证集改善时，输出“不足以更新”，保留原配置。输出 `.runtime/logs/calibration-summary.json`。

## 当前验收

140 项 Python／MCP／HTTP 测试通过，包含评分分解求和、禁止抽牌、满手及抽牌数量限制、力量多段配合、单牌与卡组分项、记录幂等、旧状态拒绝、跨会话拒绝、路径验证、标签冲突、整局分组、验证集门槛及 HTTP 接口。历史确定性出牌数值回归继续匹配；测试中的人工构造资料保存在临时目录，不进入实战库。

截至本次实现，校准库内真实选择意图 0、整局样本 0；没有生成或应用校准后的权重。本轮完成结构与采集／离线比较入口，没有启动新游戏，也没有把旧回放或人工测试算成大量实战。
