# 决策观察台：实时侧窗、历史页面与对局归档方案

日期：2026-10-11。状态：待用户核对，本文提出的功能尚未实施。本次只新增此说明，不修改窗口、游戏流程或已有存储。

## 1. 目标与当前差距

建议提供两个共用数据源的查看入口：

1. **实时侧窗**：一个独立桌面窗口，放在游戏旁边，优先展示当前状态、当前决策和执行进度。
2. **完整观察台**：通过系统默认浏览器打开大页面，查看对局总览、各幕地图、节点内的完整决策和历史。

每局归档为可单独打开、复制和备份的文件夹，按日期归类。关闭游戏、关闭窗口和重启服务后仍可查阅。

当前已有：2 秒轮询的网页观察台、动态幕次、地图节点筛选、公开快照、计算报告、明确登记的选择理由和动作回执。

当前未有：独立实时侧窗、完整的日期/对局目录、完善的对局总览、指定归档打开入口、事件推送和一致的耗时统计。现有数据按 `data/decisions/live/`、`observations/`、`replay/` 平铺保存，不能称为已完成逐局归档。

前一轮已修改观察台启动入口，使其能够请求系统默认浏览器打开；这不等于已经做出桌面侧窗。是否显示侧窗与是否打开完整浏览器页应成为两个独立选项。

## 2. 两个界面的分工

### 2.1 独立实时侧窗

第一版建议做**独立桌面窗口**，复用现有网页渲染组件。建议以 Windows 桌面程序作为轻量外壳；具体内嵌网页运行时和依赖在实施前核实，外壳代码单独放在 `src/csharp/observer/`，不混入游戏 C# 模组。

默认宽约 400 像素，可调整；可放左侧或右侧，记住大小和位置。支持置顶开关、折叠和字体调整，适配系统缩放。打开、收到新消息或重连时不主动抢游戏焦点；只有用户点击窗口时才接收交互焦点。

第一版采用可移动的普通窗口，提供贴近屏幕边缘的位置预设，不自动改变游戏分辨率或窗口大小。它不注入游戏画面。单屏空间不足时，用户可采用窗口化或无边框游戏布局；不能保证普通桌面窗口能覆盖独占全屏游戏。

建议布局：

| 区域 | 默认展示 |
|---|---|
| 顶栏 | 职业、进阶、第几幕、总楼层、房间、战斗回合；连接与记录状态 |
| 当前状态 | HP/上限、格挡、能量、金币；战斗时增加手牌容量、星星及相关异常 |
| 当前决策 | 决策序号、阶段、推荐候选、已登记的最终选择与理由 |
| 关键计算 | 预计失血、伤害、有效格挡、击杀、药水消耗、概率覆盖和未知项 |
| 执行进度 | 计划中的当前步骤、动作名称和目标、提交/结算/选牌/完成/失败 |
| 最近时间线 | 最近若干项记录，可展开；新记录提示，可暂停自动滚动 |
| 操作栏 | 返回实时、在完整观察台打开当前节点、查看详细报告 |

不同阶段切换内容：

- 战斗：候选动作及顺序、预测指标、抽牌分支、未知机制、执行结果。
- 抓牌/删牌/升级：候选、基础价值、卡组协同、约束修正、边际收益及最终选择。
- 商店：购买组合、支出、剩余金币、删牌目标、未估值条目。
- 事件：当前描述与选项、悬浮提示、已知收益/风险、重复选择次数、当前选择理由。
- 地图/休息/宝箱：当前选择、候选收益与已知后续情境。

侧窗不会为缺少模型的药水、事件等补造分数。折叠项仍保留详细数据；第一版应尽量完整，后续再按使用反馈精简。完整候选、逐步状态转移和大体积原始数据放在大页面展开，避免小窗口被原始 JSON 占满。

### 2.2 完整观察台

通过系统默认浏览器打开，保持目前的大页面形态，新增“对局总览”作为历史入口：

1. 按日期浏览，按职业、进阶、结果、游戏版本、资料完整度筛选。
2. 点击一局，查看对局摘要、动态幕次地图、实际观测到的路径、各房间记录。
3. 点击节点，按到访批次、阶段、战斗回合展开决策与执行。
4. 点击决策，查看候选、变量、评分分解、概率、提供给 AI 的资料、已登记的选择理由、动作与结果。
5. 支持打开指定归档目录或归档包，查看不在默认列表中的历史记录。

历史页面默认不会被当前新局的实时消息切走。需要明确启用跟随，或点击“返回实时”。侧窗和大页面分别维护选择、滚动位置与跟随状态，互不强制同步；“打开当前节点”才主动建立跳转。

### 2.3 打开与关闭的行为

建议统一启动入口提供三种模式：

| 模式 | 行为 |
|---|---|
| 默认游玩模式 | 启动所需本地服务，打开实时侧窗 |
| 历史查看模式 | 启动只读查看服务，在系统默认浏览器打开完整观察台；不要求游戏运行 |
| 两者同时 | 打开侧窗与完整页面，各自独立浏览 |

关闭任何查看窗口都不会自动退出游戏、终止执行服务或改变控制模式。需要停止游玩时仍由既有控制入口处理，不把窗口关闭解释为暂停指令。侧窗第一版只负责观察和导航，不增加出牌、购买等按钮。

## 3. 实时消息与显示准确性

两个界面消费相同的有序事件流。建议在现有本地服务上增加 SSE 推送；不新增专门的消息队列服务。计算仍在后台工作线程执行，事件推送不等待计算结束。

已连接时建议达到：事件成功落盘后约 1 秒内可见。该目标指界面更新延迟，不包含模型推理、搜索或游戏动画时间；通过实际测量验收，不能直接承诺所有机器上固定延迟。

每条消息有稳定 event_id、局内 sequence、UTC 时间、类型和关联 ID。客户端记住游标，断线后先补齐缺失事件，再继续订阅。网络或进程断开时显示最后更新时间与连接状态，不把旧数据冒充实时数据。保留轮询兜底，后台页面可降低刷新频率。

阶段示例：计算开始 → 分析完成 → 等待选择记录 → AI 明确选择 → 动作提交 → 游戏结算/子选择 → 执行结果 → 结果评估。允许缺项，不制造已完成阶段。

“等待选择记录”不等于能够观测 AI 内部思考；工具返回的分析、明确提交的选择理由才有依据。没登记理由时显示“未记录理由”。没有计算报告的直接动作仍保留动作记录，预测栏显示未计算。

历史和推送以同一条已落盘记录为依据：先保存，再通知。界面关闭不影响归档；重开后可以补看每一次已记录的决策。持久化失败需要显示异常并保留恢复信息，不能把未保存的信息标为已归档，也不能因重连自动重发游戏动作。

## 4. 按日期、按局保存

### 4.1 目录结构

建议采用**每局一个文件夹**，每局可导出成一个 ZIP 包便于搬运。多记录共用的索引是派生数据，不承担唯一保存职责。

```text
data/
  runs/
    2026-10-11/
      run_<稳定ID>/
        manifest.json                   # 本局元数据、状态和文件格式版本
        timeline.jsonl                  # 有序的阶段/决策/动作索引与关联关系
        summary.json                    # 可重建的统计与总览
        maps/
          act_000/
            generation_<编号>.json      # 幕内地图修订；幕数动态增加
          act_001/
          ...
        snapshots/
          <内容哈希>.json               # 原始公开状态，内容去重
        decisions/
          <decision_id>.json            # 完整计算报告、AI工具返回资料及引用
        choices/
          <choice_id>.json              # 明确登记的选择、理由和来源
        actions/
          <request_id>.json             # 请求、回执/结果引用及台账关联
        outcomes/
          <outcome_id>.json             # 实测结果、偏差与归因范围
        provenance/
          policies/                     # 实际使用过的评分参数版本
          references.json               # 游戏/桥接/规则/百科版本和指纹
    sessions/                           # 启动菜单、尚未归属新局的记录
    legacy-unassigned/                  # 旧资料无法可靠归局的记录
    .pending/                           # 服务中断时待归档数据，不能当临时缓存清理
  indexes/
    run-history.sqlite                  # 总览查询索引，可从归档重建
  replays/                              # 离线输入/回放，与实战分开标注
  knowledge/                            # 游戏知识资料，职责不变
```

日期目录直接使用 `YYYY-MM-DD` 一层，例如 `data/runs/2026-10-11/`，不拆成年/月/日多层目录。按本局开始日期分组，默认使用 Asia/Shanghai。若游戏开始时间不可取得，则用首次记录日期，并保存“首次记录时间代替开始时间”的来源说明。

跨午夜、跨日续档或重启后仍写回原本目录，不新建一局。目录名使用稳定 ID，职业和进阶通过元数据与界面展示，避免名称变化使引用失效。时间同时保存 UTC 原值、显示时区和日期分组依据；改变显示时区不会自动移动历史目录。

### 4.2 每局的独立性

打开一局时，manifest 和局内索引足以定位其地图、快照、报告、选择和动作，不依赖其他局的目录。SQLite 只加快搜索、筛选和统计；删除或损坏索引后可重建，原始归档仍可查看。

报告保存当时的计算结果、实际参数、版本指纹和必要的已引用资料，不把每次游戏都复制为一个完整百科。历史查看不自动使用新版模型重算旧分数；用户主动重算时，结果另存为离线评估，并保留原结果。

对于暂时只保存了资料指纹、没有保存解释所需原文的旧记录，明确标记依赖缺失。第一版优先保证“按原样回看”，不承诺所有旧记录都能完全重现计算。

## 5. 本局、幕、节点与到访的身份

本局使用稳定 run ID，游戏进程启动 epoch 单独记录。现有桥接的 run_history_id 可作为身份依据；还应增加身份来源与完整度说明，处理旧记录和无法确认同一存档的情况。

地图归属使用：run ID → act ID/index → map generation → coordinate。幕数从游戏提供的数据动态增加。节点不能只按“第几层”识别：不同幕、不同列、不同地图修订必须区分。

增加 **visit ID** 表示某次进入房间。一个节点内战斗、奖励、选牌和返回地图是同次到访中的不同阶段；重复进入相同节点时保留不同到访。对于游戏重载、回退或重试，保留 session/attempt 分支标记，不覆盖之前的尝试。

事件内重复选择不新建地图节点，而是在同一 visit 下追加 step 和决策。卡牌抽牌后继续行动、药水选牌、奖励子界面分别留子阶段，关联父动作。

实际路径来自成功旅行、前后节点及可靠的观测序列。缺失的连接用“中间路径未记录”表示，不能单凭两个节点都访问过就确定走过它们之间的边。

地图尚未被读取、未知节点内容和未到达幕均标注实际可知范围；完整历史页面不提前补出未知事件或奖励。

## 6. 对局总览字段

### 6.1 列表默认列

| 字段 | 含义 |
|---|---|
| 日期/开始时间 | 游戏开始时间；缺失时标注首次记录时间 |
| 职业 | 角色实体 ID 与当时名称 |
| 进阶 | 实际进入的进阶，不是当前已解锁上限 |
| 状态/结果 | 进行中、已结束、胜利、失败、放弃、未知；断线与控制暂停单独标示 |
| 进度 | 当前/最远幕、总楼层；有依据时显示节点类型和敌人/事件名称 |
| 游戏内用时 | 游戏计时；取不到则显示未知 |
| 自动游玩工作时长 | 本工具明确记录的自动控制区间内工作时长 |
| 最后更新 | 最后一次归档时间与是否仍连接 |
| 记录完整度 | 完整开始记录/中途接入/旧资料迁移/存在缺口 |

可展开更多列：游戏版本、桥接版本、决策参数版本、决策数量、动作数量、金币和最终生命。列表支持排序与分页，不能每次打开都解析所有完整快照。

### 6.2 一局详情

除列表字段外，补齐：

- 本局稳定 ID、归档路径、开始/结束/首次记录/最后记录时间、记录来源。
- 初始与最终 HP/上限、金币、牌组、遗物、药水；中途接入时初始值指首次观测值。
- 最高到达幕/层、房间访问数，普通怪/精英/Boss/事件/商店/休息/宝箱数量。
- 各战斗回合数、敌人名称、每场耗时、记录到的生命变化、击杀与终局原因。
- 抓牌、跳过、删牌、升级、购买、出售（若游戏支持并已记录）和药水使用记录。
- 决策/动作数、错误与拒绝数、子选择/人工介入次数、未知机制与模型覆盖情况。
- 计算耗时统计、执行结算耗时统计、预测与实测的偏差；无对应完整数据时不计算。
- 控制模式变化、各次进程重启、断线、续档、重试与人工接管记录。
- 游戏、桥接、协议、归档格式、模拟器、评分参数、百科/规则指纹及期间发生的版本变化。
- 结果判定来源：游戏直接提供、用户登记或根据公开状态推断，分别展示。
- 归档体积、文件数、完整性检查和可选的用户备注/标签。

统计必须注明覆盖区间和来源。HP 减少可能包含自伤，HP 增加可能包含治疗和上限变化；没有伤害事件细分时只能叫“观测生命变化”，不能当成怪物造成的净战损。未调用相应入口时，“人工介入次数”未知，不能默认填 0。

## 7. 耗时与结束状态的定义

应同时保留以下时间，避免把挂着游戏一晚算成实际游玩耗时：

| 时间 | 统计方式与限制 |
|---|---|
| 游戏内用时 | 读取游戏的计时；标记游戏自身暂停和计时语义 |
| 从开始到结束的跨度 | 结束时间减开始时间，可能包含离线和跨日 |
| 自动游玩工作时长 | 连接、处于该局、自动控制启用且无明确暂停/接管区间；包含决策等待与动画 |
| 已知暂停/人工等待时长 | 从明确的控制或等待事件形成区间；无法判断的时间不擅自扣除 |
| 计算耗时 | 本地计算器实际测量；分总量、均值、分位数 |
| 执行耗时 | 动作提交到终态回执的测量；保留超时和未知结果 |
| 选择等待时长 | 报告就绪到明确选择的间隔；可能包含 AI、用户和工具延迟，不能直接叫 AI 推理耗时 |

进程内用单调时钟统计区间，跨重启使用明确的区间记录。断开期间不计入可确认的自动工作时长，区间存在缺口时显示“至少已记录 X 分钟/覆盖不完整”。并发或嵌套计算的耗时不直接相加冒充整局墙钟时间。

正常关闭游戏只结束当前连接会话，存档仍可继续，不代表放弃。游戏公开提供明确结局时记录对应终局；无法取得时用未知。放弃需要明确动作或登记。胜利不能写死为“第三幕 Boss 死亡”，以游戏的实际终局状态为准，兼容额外幕。

## 8. 指定记录的打开方式

提供三种入口：

1. 默认历史列表：从配置的归档根目录读取，不要求游戏启动。
2. 桌面外壳的“打开对局目录”：使用系统文件选择器选 manifest 或局目录，验证后只读打开。
3. 完整浏览器页的“打开归档包”：用户选择导出的 ZIP，导入到独立记录区后查看，并标注导入来源。

浏览器不能简单凭用户填写服务器磁盘路径就取得任意本地目录；目录选择由桌面入口处理，网页以明确选择的归档包作为跨目录入口。

ZIP 导出包含一局的原始文件和 manifest，默认不带本机配置、鉴权 token 或整个知识库。导入检查格式、大小、文件哈希、相对路径和引用一致性，只解析数据，不执行其中内容。相同 run ID、不同内容时保留冲突版本，不静默覆盖已有实战局。

界面 URL 可包含 archive/run/act/visit/decision 标识，让当前节点可从侧窗跳到大页面；不在 URL 中塞本机绝对路径或鉴权信息。

## 9. 写入、性能与恢复

建议在现有常驻服务内集成归档协调器，不要求用户再启动一个归档服务。MCP 和执行器通过统一 ArchiveRepository 接口登记事件，由协调器排顺序、去重、保存和通知；中断时写到持久化 pending 区，恢复后按 event_id 补入。

每条完整公开状态按内容哈希去重。报告、选择和回执引用对应 snapshot ID，避免同一份牌组在多个文件重复出现。状态只在变化和关键边界记录，不把网页刷新当成新的游戏决策。

写入顺序：原始负载原子保存 → 时间线登记 → 索引/摘要更新 → 推送。动作派发前仍保留原有请求台账和去重保障；归档恢复不能触发重新执行。

manifest 和 summary 采用原子替换；时间线采用单写入者追加、明确刷盘和尾部损坏恢复；索引通过事务更新。程序崩溃后识别未完成写入、孤立负载和 pending，恢复引用或显示缺口，而不是整局不可打开。

总览从 SQLite 读取摘要；节点展开才加载相关报告与快照，历史时间线分页。推送只发摘要和引用，详细报告按需读取。缓存有容量限制，避免整局完整快照永久驻留内存。

显示每局和总体占用，支持手动导出/备份。第一版不自动删除实战记录；临时缓存与实战/pending 的清理边界必须分开。自动压缩、保留周期和跨机器同步可后续单独设计。

## 10. 解耦与目录职责

| 部分 | 职责 | 不负责 |
|---|---|---|
| 游戏桥接 C# | 公开状态、稳定身份、时间和终局事实 | 历史 UI、评分参数 |
| Python ArchiveRepository | 统一事件契约与归档读写 | 决定出牌 |
| Python RunIndexer | 统计摘要、查询、索引重建与迁移 | 改写原始历史结果 |
| 本地服务/API | 推送、分页查询、归档打开/导入导出 | 浏览器内部推理 |
| 网页共享组件 | 状态、候选、评分、概率、时间线 | 文件直接写入 |
| 实时视图 | 小窗口布局、跟随、连接状态 | 全局历史自动跳转 |
| 历史视图 | 日期总览、动态地图、详细回看 | 游戏控制 |
| 桌面外壳 | 独立窗口、位置、置顶、文件选择和默认浏览器跳转 | 游戏模拟与规则计算 |

建议新增 `src/python/src/autoslay/archive/`，保持 `telemetry/` 为兼容采集入口；实时/历史 UI 在 `src/web/public/` 分目录并共享展示组件；`src/csharp/observer/` 与 `src/csharp/` 游戏模组分开。

`data/knowledge/` 仍是知识资料；`data/runs/` 是实战归档。归档不会自动成为知识库或校准训练样本。评分校准应从选定、完整、版本可比的对局显式读取，不能把导入包、离线重算或缺失记录混入实战统计。

本设计文档放在 `docs/design/`；开发进度、验收结果和临时文件应分别保存。此次不顺带搬动全部旧文档。

## 11. 旧记录迁移

先做只读扫描与迁移预览，列出可可靠归局的记录、缺失字段、冲突和无法归属条目。用户核对方案后实施迁移。

有稳定身份的记录按本局合并；旧桥接只有 epoch/runtime ID 的记录仅按启动会话分组，不能仅凭职业、楼层和接近的时间把两局拼在一起。缺少开始时间用首次记录日期；缺少幕/坐标的保留为“未定位记录”。

旧决策、动作计划、选择和结果按精确 ID 与来源关联；当前不同目录间不存在可靠关联的部分保留未关联状态。离线回放单独迁移，不转成实战。

迁移默认复制，保留旧目录、来源路径和校验信息；核对记录数、引用、哈希和界面结果后再决定是否清理旧目录。旧阅读接口提供兼容层，不让一次目录变化使工具失效。

## 12. 实施顺序与验收

以下步骤在用户确认本文后才开始：

1. 定义归档/事件/身份/时间契约，增加缺失的角色、时间与终局来源字段。
2. 实现按日期逐局保存、统一采集、去重、摘要和可重建索引；保持现有记录链路兼容。
3. 接入推送与断线补发；验证两端都只展示已记录的事实。
4. 实现对局总览、筛选、分页、动态幕地图、visit 与详细决策联动。
5. 实现共享实时视图，再增加独立桌面外壳、位置/置顶配置和大页面跳转。
6. 增加指定目录/包打开、导出与导入，并完成旧数据迁移预览和兼容验证。
7. 进行一局真实游玩的链路验收，检查从开局到结束、关闭续档和异常恢复；不将 UI 夹具当实战证明。

重点验收：

- 单屏下侧窗可调整位置和大小，更新不抢焦点；完整页通过系统默认浏览器打开。
- 不运行游戏也能打开历史；关闭 UI 不终止游戏或停止归档。
- 第四幕、额外地图修订、重复到访、事件连续选择都能正确定位。
- 跨午夜和跨进程续档仍归属于同一局；不同局不会被合并。
- 每次已记录决策和动作可回看，SSE 重连无遗漏/重复展示，选择理由缺失可见。
- 跨幕动作归出发节点，新幕地图不串到上一幕；未知路径不补造。
- 时间统计不把离线当工作、不把选择等待当模型推理，缺失项明确标注。
- 断电/崩溃、索引损坏、部分文件缺失、磁盘写入失败可恢复或清楚报告范围。
- 导出的一局可在独立目录打开；导入冲突和旧版本可识别，回放不计为实战。

## 13. 建议第一版确认的默认选择

建议采用：独立可移动侧窗 + 系统默认浏览器大页面；侧窗默认约 400 像素、置顶可切换；每局目录按 Asia/Shanghai 开始日期归档；JSON 原始记录 + SQLite 派生索引；SSE 推送 + 轮询兜底；完整原始数据保留，未知项不补算；旧记录先复制迁移，不自动清理。

第一版先完成可观测和可回看的闭环，不在本轮改药水价值、卡牌权重或其他决策细节。这样 UI、存储和模型可以分别迭代。
