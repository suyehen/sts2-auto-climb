# 当前一轮完整出牌决策逻辑

核对日期：2026-10-15。本文以当前源码和本地配置为准，描述一次真实决策从输入到执行的完整计算过程。它不是固定的卡牌优先级表，也不是改进后的策略设计。

更新说明：已移除独立的一步斩杀及严格终局证明分支。可斩杀局面与其他普通战斗方案一起进入批次生成、模拟、资源评分和最终选择，不再提前按斩杀证明返回。本次没有引入整套严格模式；动作合法性、状态校验和防重复提交等执行保护继续保留。跨战斗成长、金币和遗物计数的完整价值评估仍是后续工作，不能因移除证明分支就视为已实现。

## 1. 一轮决策究竟在决定什么

当前系统不是先给每张手牌打分，再从高到低出牌。它先生成多条有顺序、有目标的操作序列，模拟每条序列造成的状态，再估计这个状态之后的战斗结果，最后选一条序列执行。

一次选择的直接产物是“当前可以执行到某个边界的操作批次”，而不是接下来整场战斗的固定出牌脚本。

例如，当前候选可以包括：

```text
方案 A：攻击甲
方案 B：攻击甲 → 格挡
方案 C：格挡 → 攻击甲
方案 D：加力量 → 攻击甲
方案 E：使用火焰药水攻击乙 → 攻击甲
方案 F：抽牌〔执行到这里停止，观察实际新手牌〕
方案 G：结束回合
```

每个方案的评分还可以包含“执行完这些步骤后，假想继续出牌、结束回合、敌人行动、下一回合抽牌和出牌”的收益。**用于评分的后续推演，不一定全部属于实际下发的批次。**

## 2. 全流程总览

```text
① 获取当前快照和实际配置
    ↓
② 检查可决策条件，处理唯一结束回合或嵌套选牌
    ↓
③ 构建战斗模型、牌组能力、地图资源价值、药水成本
    ↓
④ 确定普通/危险搜索预算
    ↓
⑤ 从当前合法动作出发，生成有顺序的候选操作批次
    ↓
⑥ 去重等价终点，并停止跨越实际观察边界的批次扩展
    ↓
⑦ 对每个批次终点继续进行假想后续搜索
    ↓
⑧ 对死亡/胜利/预测截止状态计算终点评分
    ↓
⑨ 将随机分支合并成每个批次的收益、死亡和失血指标
    ↓
⑩ 全部候选初排，再在前五名的接近分数方案中作取舍
    ↓
⑪ 复核新状态，逐步执行选中批次
    ↓
⑫ 到边界、出现偏差或批次完成，开启下一轮决策
```

下面按照这条数据流展开。当前主要执行入口为 `combat_batches_enabled = true` 的本地批次模式；校准策略 `strategy_mode = off`。

## 3. 第一步：这一轮读取什么

### 3.1 当前战斗事实

| 输入 | 用途 |
|---|---|
| 当前生命、最大生命、格挡 | 结算生存、掉血、回血和生命资源价值 |
| 能量、星数等费用资源 | 判断模拟动作能否继续执行 |
| 手牌实例、费用、目标类型、升级与修饰信息 | 编译效果并生成出牌动作 |
| 抽牌堆、弃牌堆、消耗堆组成 | 预测抽牌、洗牌、污染和后续手牌 |
| 力量、虚弱、脆弱及已覆盖能力 | 修正伤害、防御和后续状态 |
| 药水实例及合法目标 | 构造药水动作、跟踪消耗 |
| 遗物和周期计数 | 处理已经建模的触发及后续抽牌、能量 |
| 敌人生命、格挡、攻击、能力、动作历史与状态 | 模拟目标变化、敌人行动和后续分支 |
| 游戏公布的合法动作、合法目标 | 约束当前第一步及实际执行 |
| 会话、本局、战斗实例、状态版本、游戏版本 | 防止基于过期或不同上下文执行 |

### 3.2 战斗以外的估值信息

- 完整牌组的平均攻击、防御、费用和攻击段数等能力。
- 未来四步内可达的休息点、精英和 Boss。
- 燃烧之血等明确识别的战后回血。
- 每种药水的保留成本。
- 之前记录的动作模型降级信息。

### 3.3 配置和缓存

默认配置与 `.runtime/local/agent/profiles.json` 中的对应配置合并。当前战斗配置与默认值一致。

统一分析层可以复用缓存：匹配状态、知识版本、配置及相关模型状态等组成的缓存身份时，复用分析结果。执行层仍要重新获取状态并复核，不会仅凭旧缓存直接下发动作。

### 3.4 已实现：全局动作目录、对象能力和实时绑定

全局定义来自 `data/knowledge/rules/actions.json`，当前覆盖桥接全部 42 种命令。C# 桥接嵌入该文件，Python 通过知识清单读取同一文件，不再分别维护动作全集。

```text
全局动作定义（稳定 type / definition_id）
    ↓ 引用来源类别、条件、目标规则、执行适配器
实体能力档案（entity_id，含主动命令、场景操作、效果/触发/招式）
    ↓ 与当前快照的真实对象匹配
本轮动作绑定（action_id、source、allowed_target_ids、allows_no_target）
    ↓ 按真实状态校验
实际请求与执行结果
```

#### 3.4.1 这一轮怎样使用全局定义

1. 桥接根据游戏方法生成实时合法动作，核对类型及目标形状均符合全局目录。
2. 桥接 0.30.0 输出动作 `definition_id`、来源 `source`，以及 `state.action_catalog` 的版本和 SHA256。
3. 统一分析构建 `action_space`，关联每个当前动作的目录条目、来源实体/实例、对象路径及合法目标。
4. 同时记录本轮可见对象、卡牌费用和修饰等状态，以及相关实体的潜在能力和已知效果规则。
5. 决策与执行模块从公共模块读取动作分类、行政操作排除集合和目标校验逻辑。
6. 提交前仍验证新鲜游戏快照；若快照声明的目录身份不同，拒绝混用。

旧快照没有新增目录信息时可以兼容读取，但不伪造目录身份。缺少动作类型时会记录历史格式诊断，目标仍需匹配真实绑定。

#### 3.4.2 什么东西可以做什么

| 记录 | 含义 |
|---|---|
| `commands` | 实体类别能够提供的条件性命令，例如打牌、用药 |
| `contextual_commands` | 场景操作，例如商店买入、宝箱领取；不等于持有后可以主动激活 |
| `effects` | 已声明效果、周期触发、已有机制钩子及验证/来源信息 |
| `state_graph`、`moves` | 已有怪物状态图和招式，不能作为 agent 命令提交 |
| `objects` | 本轮真实实例、费用/修饰等可见状态及当前动作关联 |
| `bindings` | 当前游戏明确提供的操作和合法目标 |
| `issues` | 未注册动作、重复绑定、定义/目标/目录不一致等诊断 |

能力档案按 `entity_id` 查询，实例操作按 `instance_id` 关联；既可查对象能力，也可反查某个动作的潜在提供者。已有文本资料与可执行规则分开记录，未知能力不当作不存在。

无实时操作的对象记为 `not_exposed_currently`，不能直接推断为费用不足、没有能力或适配器不支持；只保留有来源的可用性标志。

#### 3.4.3 记录和查询

统一分析报告及本地执行报告包含完整 `action_space`，随现有决策归档保存。紧凑模型包只携带目录身份和诊断摘要。

公共 Python 模块为 `autoslay.actions`。观察台提供 `/api/actions`、`/api/actions?type=play_card`、`/api/actions?entity_id=RELIC.HAPPY_FLOWER` 和 `/api/actions/live` 只读接口。MCP 提供 `get_action_catalog`、`get_entity_capabilities`、`get_action_space`。

详细字段、兼容规则与加载方式见《全局动作目录与对象能力记录-2026-10-15.md》。目录不是新的严格斩杀模式，也不会将未经验证的观察自动升级为可执行机制。

## 4. 第二步：先决定是否进入方案搜索

按入口逻辑检查：

1. 本地决策是否开启。
2. 游戏是否连接、就绪、非忙碌、无错误、非暂停。
3. 是否有尚未处理完的父动作或选牌界面。
4. 是否具备会话、本局和状态身份。
5. 当前游戏是否通过源码认证。
6. 是否存在合法操作。

不满足可操作条件时等待。战斗嵌套选牌走第 14 节的专用分支。

正式分析前只保留必要的局部推进规则，例如没有其他合法操作时结束回合，以及战斗嵌套选牌。能直接击杀敌人不再构成跳过批次分析的理由。

完成分析后，按本轮报告中的 `selected_batch` 选择实际批次；斩杀方案与格挡、成长、药水、抽牌等方案采用相同的评分和排序流程。

### 4.1 保留的执行保护

- 必须开启本地决策；未实现的复杂策略开关不能启用。
- 游戏必须连接、无错误、就绪、非忙碌、非暂停。
- 必须有会话、本局、状态版本等身份；游戏版本和程序集必须通过现有兼容认证。
- 嵌套父动作按相应选择界面处理，不能当作普通新回合。
- 必须有合法操作，目标必须合法或明确允许无目标。
- 执行前读取新状态，核对来源；执行锁占用或状态变化时不直接提交旧方案。
- 批次每步核对同一会话、本局、战斗实例和游戏版本。
- 不重复提交结果未明确的已持久化动作，先查询原请求回执。
- 实际效果与预测不一致、遇到观察边界或上下文变化，停止当前批次。

这些保护不是独立的严格斩杀策略，不能通过更高综合分抵消。

### 4.2 移除的决策分支和旧配置兼容

已删除：

- `certain_combat_finish`：一步确定斩杀快捷选择。
- `equivalent_outcomes`：严格等价终局选择。
- `dominant_outcome`：严格支配终局选择。
- `common_first_step`：严格最佳路线共同首步选择。
- `finish_model`、`finish` 和 `terminal_comparison.py` 专用实现。

旧本地配置和导入配置仍可读取上述规则名，但会在合并时移除；它们不能重新启用旧分支。非战斗事件安全退出、奖励打开、强制推进等规则不在此次删除范围内。

### 4.3 当前批次实际保证与限制

| 条件 | 当前行为 |
|---|---|
| 报告来源、批次非空、首步合法 | 选择器硬检查 |
| 后续动作的费用、目标、手牌 | 生成时查模型，执行时查真实合法性 |
| 预计死亡概率 | 正常评分最高优先级，但不是必须零死亡才能执行 |
| 搜索完整性 | 不要求穷举，可在预算截止后近似 |
| 未知机制 | 记录假设，可能快速评价或退回文本单步估值 |
| 独立校准 | 当前不要求 |
| 实际结果偏离预测 | 停止当前批次并记录模型降级 |
| 抽牌、选牌等观察边界 | 停止连续下发，观察后再决策 |

这些近似行为仍是当前批次模式的一部分；本次移除严格证明没有将其改造成遇到一切未知就终止 agent 的模式。

### 4.4 其余代码入口的边界

当前生效的普通战斗路径为批次模式。代码仍保留 `bounded_combat_search` 当前回合备用选择器，以及默认关闭的校准策略；它们不是本次删除的一步斩杀或终局证明分支。

当前配置保持 `combat_batches_enabled=true`、`strategy_mode=off`。只有更改配置或调用其他策略入口时，才可能使用上述备用逻辑。本文后续章节描述当前实际批次路径，不将备用策略作为批次结果的额外审核。

## 5. 第三步：为本轮构建模型和预算

### 5.1 战斗模型

将快照标准化为模拟状态，并编译手牌与药水效果。模拟动作会更新费用、手牌、敌人生命、格挡、力量、牌堆等已覆盖字段。

批次预测使用 `forecast_state` 清空基础模拟中的 `warnings` 和 `mechanism_scope` 阻断字段，将原始警告另外存入假设记录。也就是说，批次模式允许在未完整覆盖机制时继续估计，不代表完整机制覆盖。

敌人模型根据当前状态和动作历史准备后续动作。第一回合若只有一个无条件初始动作，而且与可见攻击一致，可以推断初始动作状态，并记录该假设。

### 5.2 搜索预算

| 条件 | 节点 | 时间 | Top-K |
|---|---:|---:|---:|
| 普通 | 2000 | 200 ms | 5 |
| 危险 | 6000 | 400 ms | 5 |

危险条件为生命比例 ≤35%、可见攻击总量 ≥当前生命、当前地图节点为 Boss，任意满足即可。此判断未先扣除格挡。

当前批次最大深度为 6；预测包含当前及下一玩家回合，分支上限 32，种子 42，下一回合基础抽牌 5、基础能量 3。

时间限制是搜索循环中的预算检查，不表示整个请求墙钟时间严格不超过 200/400 ms。

## 6. 第四步：怎样生成所有候选出牌方案

这里的“所有”指预算内生成并保留的候选，不是穷举全部可能出牌、随机结果和整场战斗。

### 6.1 第一层：从真实合法动作出发

先把游戏合法动作展开为具体操作：

```text
攻击牌 A 可打甲或乙
    → 操作：A→甲
    → 操作：A→乙

格挡牌 B 无需目标
    → 操作：B

火焰药水可打甲或乙
    → 操作：火焰药水→甲
    → 操作：火焰药水→乙

结束回合
    → 操作：结束回合
```

主动弃药、退出游戏、返回主菜单不参加批次搜索。

### 6.2 后续层：按模拟状态重新生成动作

采用队列进行广度优先扩展。每次从队列取出：

```text
当前模拟状态 + 已经走过的操作序列
```

对非空序列先登记一个候选终点，然后判断还能否延伸。可延伸时：

1. 根据新状态重新计算模拟合法动作。
2. 检查剩余能量、星数、手牌、存活目标与已编译效果。
3. 为每个动作和目标生成后继。
4. 另行加入结束回合。
5. 将新状态和更长操作序列放回队列。

因此“攻击→格挡”和“格挡→攻击”首先是不同路径；加能量或加力量后，也会用更新后的状态继续展开。

动作按 `action_id`、`target_id` 稳定排序后扩展。它们不是牌面价值优先级，但在预算有限时会影响哪些路径来得及生成。

### 6.3 每个中间状态都可以是方案

一条路径：

```text
A → B → C
```

可以产生 `[A]`、`[A,B]`、`[A,B,C]` 三个批次候选。候选不要求打光手牌或能量。

`batch_goal_completed` 在这里可以只是“选择在这个操作前缀末尾结束批次”，不是系统完成了一个独立识别的战术目标。

### 6.4 哪些地方不能继续生成实际批次

- 发生抽牌等需要观察的边界。
- 发生模型降级观察边界。
- 战斗胜利、玩家死亡。
- 已达到最大批次长度。
- 已达到批次生成时间或节点预算。

生成阶段最多约占 40% 时间预算和一半节点预算。剩余预算用于后续评价。

### 6.5 等价终点去重

终点身份包含战斗状态、观察边界、尚未恢复的效果、待抽牌数量、待处理卡牌和效果目标等。计算身份时忽略可互换手牌实例 ID。

相同终点已有不长于当前路径的方案时，跳过当前路径，避免重复占位。去重不按首步分组，所以不同首步到达同一终点，可能只保留其中一条。

生成结束后，会尝试补回尚未代表的当前合法首步；但等价终点仍可能合并，因此并非每个首步都有独立评分行。第一步无法模拟时，保留单步未知效果候选。

## 7. 第五步：每个候选不是只看打完后的面板

批次生成结束后，先对可模拟候选、较长批次等进行稳定排序，再逐个评分。所有候选共享这一轮搜索预算，并非每条方案有独立的完整预算。

每个可模拟批次，从它的终点调用后续搜索 `visit`。后续搜索返回：

- 预计综合分 `score`。
- 预计死亡指标 `death`。
- 预计最坏净失血 `loss`。
- 分项收益 `parts`。
- 近似计数 `unknown`。
- 后续路径涉及的药水集合 `used`。

### 7.1 普通终点：比较继续出牌和现在结束回合

如果没有边界，先算“现在结束回合”的结果，再尝试继续每个模拟合法动作。

这些假想后续中，选择：

```text
预计死亡指标最小 → 综合分最高
```

此处不会再用最终批次阶段的“分差 1 分内省药优先”规则。

假想后续的回合内深度受 `min(5, max_depth)` 限制；当前批次已打步骤数作为初始深度传入，进入下一玩家回合后深度归零。

因此 `[A]` 的估值可能包含“打完 A 以后，再打 B 才更好”，而实际批次仍然只有 A。批次边界与评分续算范围是两回事。

### 7.2 抽牌终点：按可能的新手牌分支续算

1. 根据牌堆组成、手牌空间、抽牌限制和可建模洗牌计算抽牌计划。
2. 小规模结果精确枚举；结果多时固定种子采样。
3. 为抽到的卡构造假想手牌。
4. 恢复抽牌之后尚未结算的卡牌效果。
5. 对每种手牌分别寻找较好的后续。
6. 将分支结果按概率合并。

未知卡牌模板或无法恢复的分支不会直接被丢弃，而是使用快速近似评价。实际执行只打到抽牌边界，等待真实抽牌结果。

### 7.3 模型降级终点

实际执行要在降级动作后观察；评分仍移除这一边界，假想继续预测，然后额外增加一次近似并扣 3 分，避免遗漏当前敌人回合代价。

### 7.4 其他观察边界

使用快速评价 `quick`，通常尝试模拟一次敌人行动并计算终点，不完整展开后续玩家回合。

### 7.5 到预算或死亡/胜利

- 玩家死亡或战斗胜利：直接终点评价。
- 节点或时间预算耗尽：使用快速评价。
- 相同 `(transition, ply, depth)` 复用已算结果。

## 8. 第六步：结束回合和下一回合怎样推演

当某条假想路线选择结束回合：

1. 按当前实现将手牌放入弃牌堆；`CARD.ASCENDERS_BANE` 单独进入消耗堆。
2. 若有未建模手牌的回合结束效果，记录假设并追加未知惩罚。
3. 使用敌人规则执行敌人回合，并选择后续动作分支。
4. 已死亡、胜利或到预测回合上限的分支直接终点评价。
5. 其余分支尝试进入下一玩家回合。
6. 更新已覆盖的周期遗物；计数未知或抽牌被阻断等情况会提前终点评价并增加未知。
7. 清空格挡，以配置基础能量 3 加遗物加成重置能量。
8. 扣除临时力量并迁移持续力量，更新部分状态和敌人易伤剩余回合。
9. 按 5 张基础抽牌加遗物加成生成下一手牌分支。
10. 对下一回合继续执行第 7 节搜索。

这是当前实现的结算模型，不代表所有手牌保留、消耗、能力和遗物触发都已覆盖。

敌人模型失败时，以存活敌人的可见攻击逐段扣除格挡和已覆盖减伤，计算失血，再加未知惩罚。此回退不会证明未知非攻击效果没有影响。

## 9. 第七步：如何给一个预测终点打分

设该预测终点为 S、当前实际起点为 S₀：

```text
Q(S)
= 生命资源差值
+ 远期压力生命价值
+ 50 × 是否胜利
− 0.4 × 存活敌人剩余生命总量
− 污染牌数量
− 已消耗药水保留成本
− 3 × 显式未知单位数
− 10000 × 是否死亡
```

当前 `player_growth`、`enemy_growth` 两个独立评分项均为 0。

### 9.1 生命资源差值

```text
V(h) = 2 × [h − 3 × (M − h)³ / (3 × M²)]
       − R × max(0, M×r − h) / max(1, M×r)

生命资源差值 = V(终点生命及适用战后回血) − V(起点生命及适用基准回血)
```

其中：

- `M` 是最大生命，`h` 截断到 `[0,M]`。
- `r = min(0.7, 0.4 + 0.12×p)`。
- `p` 为未来四步可达精英/Boss 的最大 `1/距离`。
- 无可见休息点时 `R=8`；最近休息点距离 d 时 `R=8×(1+1/d)`。

低血时掉血更贵，低于保留线另有惩罚。当前明确识别燃烧之血战后回复 6 点；胜利终点和比较起点都应用各自可得的回血，避免误算免费失血。

### 9.2 远期压力生命价值

根据完整牌组（无牌组时使用手牌）平均能力估计：

```text
u = min(1, 3 / max(1, 5×平均能量需求))
D = max(1, [平均伤害 + 持续力量×平均攻击段数]×5×u)
B = 平均格挡×5×u

虚弱：D×0.75；脆弱：B×0.75
预计收尾回合数 = min(4, 敌人总生命及格挡 / D)
预计额外失血 = max(0, 当前敌方攻击总量−B)×预计收尾回合数
远期压力价值 = [V(扣除预计失血后的生命)−V(当前生命)]×0.5
```

终点敌人均无攻击时，会尝试查看一次非攻击动作之后的压力，按分支加权。这个窥看只改压力代理，不直接给当前轨迹添加假想回血或伤害。

### 9.3 药水成本

| 药水 | 成本区间 | 正常使用的中点 |
|---|---:|---:|
| 火焰 | 8～20 | 14 |
| 格挡 | 6～14 | 10 |
| 能量 | 6～18 | 12 |
| 力量 | 8～20 | 14 |
| 未配置成本 | 未知 | 20 |

同种持有多瓶时成本乘 0.75；药水栏满且明确存在可领取药水奖励时再乘 0.5。消耗的每瓶药只扣一次。

### 9.4 污染与未知

污染只计抽牌堆、弃牌堆中键含 `SLIMED`、`DAZED`、`WOUND`、`STATUS` 的牌，每张扣 1。未知扣分来自具体预测调用传入或追加的未知计数，不是所有警告统一乘 3。

### 9.5 为什么没有固定攻击/防御优先级

正常批次不直接给每点格挡加 1.5 分或每点伤害加 1 分：格挡主要通过少掉血获得收益；伤害通过击杀、减少敌方行动、降低剩余生命和远期压力获得收益。

因此加力量、抽牌、攻击和格挡的先后关系，由更新状态之后的整体结果决定。顶层旧评分权重不等于这里的主评分。

## 10. 第八步：随机分支怎样合并成方案指标

若分支 i 的概率为 pᵢ、分数为 Qᵢ、死亡为 dᵢ、净失血为 Lᵢ：

```text
方案分数 = Σ(pᵢ×Qᵢ) / Σpᵢ
方案死亡指标 = Σ(pᵢ×dᵢ) / Σpᵢ
方案最坏净失血 = max(Lᵢ)
```

终点 `dᵢ` 为玩家生命≤0 时的 1，否则为 0。终点 `Lᵢ=max(0,起点生命−终点生命)`，所以它是净失血，不是沿途受到伤害总量；先受伤后回血可能抵消它。

其他合并规则：

- 分项收益、生命资源项按概率加权。
- 近似计数取分支最大值，非精确采样再加 1。
- 药水集合取所有分支用药的并集。
- 没有有效概率质量时，回到起始状态终点评价并增加未知。

两个容易影响最终选择的细节：

1. 分支并集包括假想后续药水，不一定全部出现在当前实际批次中。
2. 采样使近似计数增加，并不意味着分支平均分会在合并时自动再减 3；评分惩罚与近似统计不是同一个字段。

## 11. 第九步：每条出牌方案最终保存什么

| 字段 | 含义 |
|---|---|
| `steps` | 这一批真正计划下发的有序操作及目标 |
| `stop_reason` | 该批次终点或观察边界 |
| `score` | 包括假想后续在内的方案估计分 |
| `utility_components` | 各评分项 |
| `estimated_death_probability` | 模型/采样下的预计死亡指标 |
| `estimated_worst_hp_loss` | 各预测分支最坏净失血 |
| `approximation_count` | 后续近似计数加原始标准化警告数量 |
| `consumed_potions` | 预测分支涉及药水的并集 |
| `endpoint` | 当前批次结束时的生命、能量、格挡和敌人生命 |
| `state_trace` | 为前五名补充的批次状态轨迹 |

注意 `endpoint` 是批次终点，`score` 可以看得更远；仅看终点面板不一定能解释评分。

## 12. 第十步：全部方案怎样比较并选出唯一方案

### 12.1 先对全部候选排序

优先级从高到低：

1. 预计死亡概率更低。
2. 综合分数更高。
3. 近似次数更少。
4. 实际批次步骤更多。
5. 批次 ID 更靠前，稳定打破平局。

这不是把五项相加，而是依次比较：前一项不同，后面就不能抵消前面的差异。

### 12.2 再建立接近分数候选池

只取上一步前 5 名，并要求：

```text
死亡概率 == 第一名死亡概率
第一名分数 − 本方案分数 ≤ 1.0
```

没有“死亡概率差不多”的容忍区间，代码使用相等比较。

### 12.3 接近分数池重新选一个

依次优先：

1. 预测消耗药水数量更少。
2. 最坏净失血更少。
3. 近似次数更少。
4. 当前批次步骤更多。
5. 批次 ID 稳定打破平局。

最高分方案可能因此被替换；最高分不是唯一决策依据。

### 12.4 一个完整的最终选择示例

下表为说明排序而构造的示例数据，不是本次真实对局记录：

| 方案 | 死亡概率 | 综合分 | 预测用药数 | 最坏净失血 | 近似数 | 批次步数 |
|---|---:|---:|---:|---:|---:|---:|
| A：药水→攻击 | 0 | 20.0 | 1 | 0 | 0 | 2 |
| B：格挡→攻击 | 0 | 19.4 | 0 | 2 | 0 | 2 |
| C：攻击 | 0 | 19.2 | 0 | 1 | 1 | 1 |
| D：加力量→攻击 | 0 | 18.8 | 0 | 0 | 0 | 2 |
| E：全力攻击 | 0.1 | 60.0 | 0 | 8 | 0 | 3 |

选择过程：

1. E 即使分数最高，死亡概率更高，初排仍落后于零死亡候选。
2. A 是零死亡中的最高分，接近范围为 19.0～20.0。
3. A、B、C 进入接近池；D 不进入。
4. B、C 不用药，优先于 A。
5. C 最坏净失血 1，优于 B 的 2，因此最终选 C。
6. C 的近似更多、步骤更少都排在最坏净失血之后，不能改变此结果。

## 13. 两条异常评价路径

### 13.1 只有某个动作无法模拟

保留该动作的单步候选：

```text
候选估值 = 对当前初始状态进行快速敌人回合估值 + 动作文本估值
```

文本估值：卡牌费用每点 −1；伤害每点 +1；格挡每点 +1.5；抽牌每张 +3；力量每点 +3；回血/失血使用生命函数；药水起始 −20。

该动作文本并不会真实改变模拟状态。所以它通常不会在这条回退里减少预测敌人攻击或死亡指标；未知药水的分支消耗集合也不等于其真实消耗。

### 13.2 整个状态标准化失败

完全跳过正常批次模型，为每个当前合法操作创建单步候选，直接按文本分从高到低、再按 ID 排序。死亡概率与最坏失血记录为未知，也不走正常接近分数取舍。

结束回合通常没有匹配文本，文本分为 0。此路径是现有退化行为，不代表它对复杂局面进行了生存判断。

## 14. 第十一步：遇到战斗嵌套选牌怎么决策

父动作尚未完成、界面要求选牌时，当前批次停在这里，另做一次观察选择：

1. 界面未就绪则等待。
2. 已选数达到最低数量且可确认，直接确认。
3. 否则对每张候选牌使用第 13 节文本估值。
4. 提示含 `discard`、`exhaust`、`移除`、`消耗`、`弃` 时，选择低分牌；否则选高分牌。
5. 分数相同按动作 ID 打破平局。
6. 一次只做一个选择动作，再观察。

最低数量没有有效正整数时按 1 处理。当前没有完整搜索“选掉这张后，剩余手牌能形成什么组合”。

## 15. 第十二步：最终方案怎样实际执行

最终选择不是直接把假想搜索树全部交给游戏。执行层：

1. 重新获取实际状态，对照分析来源和状态版本。
2. 再资格检查，必要时重新取得对应分析结果。
3. 对最终 `selected_steps` 逐步下发。
4. 每步检查当前动作和目标合法，并使用当前版本提交。
5. 动作提交前持久化请求身份，避免重复提交。
6. 执行后获取实际状态，与该步预测对比。

满足任一情况停止批次并重新决策：

- 原定批次完成。
- 打出抽牌等产生观察边界的效果。
- 出现选牌界面。
- 结束回合。
- 战斗结束、阶段/会话/本局/战斗实例改变。
- 当前状态不可操作或动作不再合法。
- 模拟不可用、预测与实际不一致。
- 手牌描述、修饰、费用、最大生命等核对资源意外改变。
- 动作失败、拒绝或结果尚未确定。

预测不一致会登记对应卡牌/药水模型降级，后续在该动作后尽量停止连续执行。当前本地记录有 `CARD.SETUP_STRIKE`、`CARD.STRIKE_IRONCLAD`、`CARD.MOLTEN_FIST`；这不是禁用清单，也不是本次重新验证的结论。

如果批次模式没有可执行结果，代理等待本地重新分析，不自动交给大模型战斗决策。

## 16. 一轮算法伪代码

```python
def decide(snapshot):
    if not ready_and_certified(snapshot):
        return WAIT
    if combat_nested_selection(snapshot):
        return choose_one_visible_selection(snapshot)
    if only_legal_action_is_end_turn(snapshot):
        return end_turn()

    cfg = effective_configuration()
    budget = danger_or_normal_budget(snapshot, cfg)
    model, deck, route, potion_costs = prepare(snapshot, cfg)
    if normalization_failed(model):
        return highest_text_score_single_action(snapshot)

    candidates = breadth_first_generate_batches(
        real_legal_first_actions=snapshot.legal_actions,
        later_actions=simulated_legal_actions,
        max_depth=6,
        stop_at_observation=True,
        deduplicate_endpoints=True,
        generation_budget=part_of(budget),
    )
    candidates = try_supplement_missing_legal_first_actions(candidates)

    for batch in evaluation_order(candidates):
        if batch.effect_unmodeled:
            value = quick_enemy_turn_value(initial_state)
            value.score += visible_text_score(batch.first_action)
        else:
            value = forecast_from_endpoint(
                batch.endpoint,
                horizon=2,
                compare_continuations_by=(LOWER_DEATH, HIGHER_SCORE),
                draw_and_monster_branches=True,
                shared_budget=budget,
            )
        batch.metrics = value

    ordered = sort(candidates, by=(
        LOWER_DEATH, HIGHER_SCORE, FEWER_APPROXIMATIONS,
        MORE_BATCH_STEPS, STABLE_ID,
    ))
    close = [b for b in ordered[:5]
             if b.death == ordered[0].death
             and ordered[0].score - b.score <= 1.0]
    chosen = min(close, by=(
        FEWER_FORECAST_POTIONS, LOWER_WORST_NET_HP_LOSS,
        FEWER_APPROXIMATIONS, MORE_BATCH_STEPS, STABLE_ID,
    ))
    return chosen.actual_steps

def execute(chosen):
    revalidate_fresh_state()
    for step in chosen.actual_steps:
        verify_legal_action_and_target()
        persist_and_submit_once(step)
        observe_actual_state()
        if boundary_or_mismatch_or_context_change():
            break
    return REDECIDE
```

伪代码省略了缓存、日志和部分错误处理，具体分支以前文和源码为准。
